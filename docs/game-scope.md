# NAN 2026 예선 빌드 스코프

작성일: 2026-07-26 (2026-07-26 전면 개정)

## 0. 개정 사유

초판은 사전 과제의 `AI 활용`을 **게임 안에 AI 기능을 넣는 것**으로 해석하여, 무기 3종 규모로 축소하고 정적 AI 빌드 추천 데이터를 핵심 AI 활용 요소로 삼았다. 이 해석은 잘못되었다.

참가 약관 제4조 1항은 `출품작 개발에 사용한 주요 AI 도구의 명칭과 활용 방식`을 고지하도록 하고, 제출물 4번은 `AI 도구·프롬프트·활용 내역`을 요구한다. 본행사는 `주제 공개와 동시에 48시간 개발`이며 수상자 전원이 최종 면접으로 직행한다. 즉 평가 대상은 **AI 코딩 에이전트를 구동해 개발하는 능력**이다.

따라서 이 개정판은 두 가지를 바꾼다.

1. 게임 안의 AI 기능을 전부 삭제한다. 초판 8.1 `AI 디렉터: 빌드 추천 데이터`는 폐기한다.
2. 스코프를 축소가 아니라 **확대**한다. 단, 기능 개수를 늘리는 것이 아니라 조합 가능한 시스템을 만들고 콘텐츠를 데이터로 채우는 방향으로 확대한다.

## 1. 한 줄 소개

무기와 보조능력을 조합해 매 판 다른 빌드를 만드는 웹 기반 2D 탑다운 액션 로그라이트.

## 2. 전제

- **2인 팀 참가. 기획 1명, 개발 1명.** 팀원 롤 기술서를 포함해 제출물은 5종이다.
- 개발 인력은 1명이므로 아래 스코프 상한은 그대로 유지한다. 다만 조합 검증과 밸런스 플레이 테스트는 기획 담당이 분담하므로, 이 스코프의 최대 리스크인 QA 표면적은 1인 개발 단독일 때보다 완화된다.
- 마감: 2026-08-10 23:59:59 KST. 기능 동결: 2026-08-05.
- 심사자는 링크 클릭만으로 브라우저에서 즉시 플레이한다.
- 런타임에 외부 AI API를 호출하지 않는다. 게임은 순수한 클라이언트 빌드다.

## 3. 설계 원칙

이 스코프의 핵심 판단은 **개별 기능을 쌓지 않고 엔진을 만든 뒤 콘텐츠를 데이터로 채운다**는 것이다.

원안 `01. 기획초안.xlsx`의 보조능력 23종은 23개의 개별 기능이 아니라 3개 서브시스템에서 파생되는 데이터다. 엔진 3개를 제대로 만들면 보조능력 대부분이 JSON 행으로 떨어진다. 이 구조는 하드코딩보다 구현 비용이 낮으면서, 제출용 AI 활용 기술 문서에서 `에이전트에게 기능을 하나씩 시켰다`가 아니라 `조합 가능한 시스템을 설계하고 콘텐츠를 데이터로 뽑았다`는 주장을 가능하게 한다.

동시에 이 원칙은 스코프의 상한도 정한다. 조합 공간이 넓어질수록 **QA와 밸런스 표면적**이 곱으로 커지는데, 이 검증은 에이전트가 대신 해주지 못한다. 무기 6종 × 보조 23종이면 조합이 138개이고 마감까지 전부 만져볼 수 없다. 따라서 무기 4종 × 보조 15종 규모로 상한을 둔다.

## 4. 원안 두 파일의 충돌 정리

`01. 기획초안.xlsx`와 `02. 전투시스템 초안.xlsx`는 서로 다른 시점의 초안이며 내용이 충돌한다.

| 항목 | 01 | 02 | 예선 채택 |
| --- | --- | --- | --- |
| 무기 | 9종 (도끼·총·소환수 포함) | 6종 | 02 기준에서 4종 |
| 상태이상 | 출혈/가중출혈/피석화/기절/탈진/원소 | 벌어진 상처/약점 노출/골절/균열/낙인/중독 | **02 명칭 사용** (수치가 정의되어 있음) |
| 보조능력 | 23종 상세 정의 | 빈 시트 | **01 사용** |
| 콤보 발동 스킬 | 검 7종 상세 정의 | 빈 시트 | **01에서 발췌** |

02의 `02_발동스킬`, `03_보조젬`, `05_핵`, `06_증강`, `07_유물`, `08_패시브트리`는 헤더만 있는 빈 시트다. 실제 설계 자산은 01에 있으므로 상태이상 명칭만 02를 따르고 나머지 콘텐츠는 01에서 가져온다.

## 5. 핵심 루프

```
무기 2종 선택 (좌클릭 / 우클릭)
  → 웨이브 1 → 보조능력 3택1
  → 웨이브 2 → 보조능력 3택1
  → 웨이브 3 → 보조능력 3택1
  → 보스 → 승리 / 패배 → 재시작
```

- 한 판 3-5분
- 보조능력을 3회 장착하면서 같은 무기가 눈에 띄게 다르게 동작한다
- 이 선택 구간이 로그라이트 성립 조건이자, 30-60초 영상에서 시스템 깊이를 보여주는 장치다

| 무기 | 아키타입 | 기본 공격 | 상태이상 | 콤보 발동 스킬 |
| --- | --- | --- | --- | --- |
| 검 | 근접 지속딜 | 전방 스윙 | 벌어진 상처 | 멸검 (지대 생성) |
| 활 | 원거리 약점 | 직선 투사체 | 약점 노출 | 다중 사격 (투사체) |

망치와 클로는 제외한다. 망치는 검과, 클로는 검·활과 아키타입이 겹쳐 늘려도 새로운 것을 보여주지 못한다.

## 8. 3개 서브시스템과 보조능력 15종

보조능력은 선택한 무기의 기본 공격 또는 콤보 발동 스킬에 장착되어 성질을 바꾼다.

### 8.1 투사체 조합 엔진 (7종)

투사체의 생성·분열·충돌 이후 거동을 조합 가능한 규칙으로 처리한다.

| 보조능력 | 효과 |
| --- | --- |
| 다중투사체 | 투사체 수 +2, 투사체 피해 40% 감소 |
| 갈래 | 갈라지는 투사체 수 +3, 투사체 피해 40% 감소 |
| 관통 | 관통 횟수 2회 |
| 상위 관통 | 모든 대상 관통 |
| 연쇄 | 연쇄 +2, 연쇄마다 피해 20% 감소, 동일 대상 2회까지 |
| 튕겨쏘기 | 지형 충돌 후 1회 추가 튕김 |
| 투사체 속도 증가 | 속도 50% 증가, 피해 20% 증가 |

우선순위 규칙은 원안을 따른다: `관통 > 연쇄 > 갈래 > 튕겨쏘기`

### 8.2 지대 엔진 (4종)

지대는 위치·반경·지속시간·틱 간격·피해 타입을 갖는 엔티티다. 콤보 발동 스킬 중 멸검과 균열 파동이 지대를 생성한다.

| 보조능력 | 효과 |
| --- | --- |
| 폭발하는 지대 | 생성 2초 후 폭발, 물리 피해의 40%를 화염으로 전환, 점화 지대 2초 생성 |
| 찌릿거리는 지대 | 감전 지대로 전환, 지속시간 +1초, 물리 피해 50%를 번개로 전환 |
| 끌어내리는 지대 | 냉각 지대로 전환, 지속시간 +2초, 물리 피해 50%를 냉기로 전환 |
| 지진 | 효과 범위 100% 증가, 지속피해 간격 50% 가속, 피해 20% 감소, 적 이동 방해 |

### 8.3 범용 수정자 파이프라인 (4종)

원안의 계산 규칙을 그대로 구현한다: **증가/감소를 먼저 합산한 뒤 증폭/감폭을 곱연산으로 적용한다. 증가·증폭은 곱하기, 감소·감폭은 나누기.**

| 보조능력 | 효과 |
| --- | --- |
| 부귀 | 보조 대상 스킬 피해 25% 증가 |
| 과감한 결단 | 콤보 지속시간 100% 증폭, 콤보 50% 확률 2배 획득, 피해 10% 증가 |
| 추가 중첩 | 중첩 가능 횟수 +1, 피해 10% 감소 |
| 지속되는 평정 | 지속시간 50% 증폭 |

### 8.4 여유가 있을 때 추가 (스트레치)

엔진이 이미 있으므로 데이터 추가만으로 확장된다. 08-05 기능 동결 전에 여유가 있을 때만 넣는다.

살얼음, 고통의 지대, 끔찍한 지대, 투사체 속도 감소 → 최대 19종

## 9. 콤보 시스템

- 기본 공격 명중 시 콤보 게이지 증가
- 목표 콤보 도달 시 다음 공격이 해당 무기의 콤보 발동 스킬로 전환
- 콤보는 기본 지속시간 내에 유지되지 않으면 초기화 (원안 규칙)
- MVP에서는 자동 발동으로 단순화하고, 여유가 있으면 수동 발동을 추가한다

## 10. 데이터 스키마 방향

보조능력과 무기는 코드가 아니라 데이터로 정의한다. 이 구조 자체가 제출 문서의 핵심 소재다.

```ts
type Support = {
  id: string;
  name: string;
  tags: Tag[];              // 투사체 / 지대 / 지속시간 / 중첩 / 공격 ...
  appliesTo: Tag[];         // 이 태그를 가진 스킬에만 장착 가능
  modifiers: Modifier[];    // { stat, mode: 'increase'|'more'|'reduce'|'less', value }
  behaviors?: Behavior[];   // { kind: 'pierce'|'chain'|'fork'|'convert', params }
};
```

태그 시스템이 장착 가능 여부를 결정하므로, 잘못된 조합이 애초에 만들어지지 않는다. 이것이 QA 표면적을 줄이는 핵심 장치다.

## 12. 기술 스택

- **Vite + TypeScript**
- **Phaser 4** (4.2.1)
- GitHub Pages 배포
- 제출 문서는 Markdown 작성 후 PDF 변환

Phaser를 선택한 이유는 이 게임이 투사체와 지대 엔티티를 대량으로 생성하기 때문이다. 충돌 처리와 스프라이트 풀링을 그대로 쓸 수 있어, 순수 Canvas로 갈 때 직접 만들어야 하는 비용이 사라진다. 번들은 빌드 기준 1.38MB(gzip 359KB)로 GitHub Pages에 문제되지 않는다.

버전은 계획 단계에서 Phaser 3으로 적었으나, 설치 시점의 최신 버전이 **4.2.1**이어서 4를 채택했다. 타이틀 화면과 플레이 씬을 실제로 렌더링해 동작을 확인했다. 다만 Phaser 4는 렌더러가 새로 쓰인 메이저 버전이라 참고 자료가 3보다 적다. 지대·투사체를 대량으로 그리는 M3 단계에서 렌더링 문제가 나오면 Phaser 3으로 내리는 선택지를 열어둔다. 현재 Phaser에 직접 의존하는 코드는 `main.ts`와 씬 2개뿐이라 지금 시점의 교체 비용은 작다.

## 14. 제출용 설명 포인트

- 그 결과 보조능력 15종이 코드가 아닌 JSON 행으로 존재하며, 조합 폭발을 태그 시스템으로 제어했다
- AI 코딩 에이전트에게 넘긴 작업과 사람이 직접 잡은 작업의 경계를 기록으로 남겼다
- 밸런스와 조합 검증은 에이전트가 대신할 수 없는 영역이었고, 여기서 스코프 상한을 정했다
