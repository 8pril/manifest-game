# NAN 2026 예선 빌드 스코프

작성일: 2026-07-26  
최종 수정: 2026-08-01

> 상태: **최신 예선 빌드 스코프 요약**
> 상세 기획과 장기 확장 방향은 `docs/full-concept-implementation-plan.md`를 기준으로 한다.

## 1. 한 줄 소개

검 하나로 시작해 보스 드랍과 마을 장비 설정으로 양손 무기 조합을 확장하는 웹 기반 2D 탑다운 핵앤슬래시.

## 2. 전제

- **2인 팀 참가. 기획 1명, 개발 1명.** 팀원 롤 기술서를 포함해 제출물은 5종이다.
- 개발 인력은 1명이므로 아래 스코프 상한은 그대로 유지한다. 다만 조합 검증과 밸런스 플레이 테스트는 기획 담당이 분담하므로, 이 스코프의 최대 리스크인 QA 표면적은 1인 개발 단독일 때보다 완화된다.
- 마감: 2026-08-10 23:59:59 KST. 기능 동결: 2026-08-05.
- 심사자는 링크 클릭만으로 브라우저에서 즉시 플레이한다. 서버나 외부 API에 의존하지 않는 순수 클라이언트 빌드다.

## 3. 설계 원칙

이 스코프의 핵심 판단은 **개별 기능을 쌓지 않고 엔진을 만든 뒤 콘텐츠를 데이터로 채운다**는 것이다.

원안 `01. 기획초안.xlsx`의 보조능력 23종은 23개의 개별 기능이 아니라 3개 서브시스템에서 파생되는 데이터다. 엔진 3개를 제대로 만들면 보조능력 대부분이 JSON 행으로 떨어진다. 이 구조는 하드코딩보다 구현 비용이 낮으면서, 제출용 AI 활용 기술 문서에서 `에이전트에게 기능을 하나씩 시켰다`가 아니라 `조합 가능한 시스템을 설계하고 콘텐츠를 데이터로 뽑았다`는 주장을 가능하게 한다.

동시에 이 원칙은 스코프의 상한도 정한다. 조합 공간이 넓어질수록 **QA와 밸런스 표면적**이 곱으로 커지는데, 이 검증은 에이전트가 대신 해주지 못한다. 무기 6종 × 보조 23종이면 조합이 138개이고 마감까지 전부 만져볼 수 없다. 따라서 무기 4종 × 보조 15종 규모로 상한을 둔다.

## 4. 원안 두 파일의 충돌 정리

`01. 기획초안.xlsx`와 `02. 전투시스템 초안.xlsx`는 서로 다른 시점의 초안이며 내용이 충돌한다.

| 항목 | 01 | 02 | 예선 채택 |
| --- | --- | --- | --- |
| 무기 | 9종 (도끼·총·소환수 포함) | 6종 | 02 기준에서 4종 |
| 상태이상 | 출혈/가중출혈/피석화/기절/탈진/원소 | 벌어진 상처/약점 노출/골절/균열/낙인/중독 | **02 명칭 사용** (수치가 정의되어 있음) |
| 보조능력 | 23종 상세 정의 | 빈 시트 | **01 사용** |
| 콤보 발동 스킬 | 검 7종 상세 정의 | 빈 시트 | **01에서 발췌** |

02의 `02_발동스킬`, `03_보조젬`, `05_핵`, `06_증강`, `07_유물`, `08_패시브트리`는 헤더만 있는 빈 시트다. 실제 설계 자산은 01에 있으므로 상태이상 명칭만 02를 따르고 나머지 콘텐츠는 01에서 가져온다.

## 5. 핵심 루프

```
검 1종, 콤보스킬/R링 잠금 상태로 시작
  → 흐린 입구 정리 → 멸검 드랍 아이템 접근 → 자동 획득 → 출구로 이동
  → 첫 문지기 처치 → 바닥 드랍 아이템 접근 → 자동 획득
  → 마을 방 진입 → NPC 근처 F 대화 → 장비/R링 후보 설정
  → 해금 시험장 → 파편 회랑
  → 무너진 문 처치 → 바닥 드랍 아이템 접근 → 자동 획득
  → 승리 / 패배 → 재시작
```

- 한 판 3-5분
- 웨이브 사이 보조능력 3택1은 폐기한다
- 흐린 입구 클리어 보상으로 검 콤보스킬 `멸검`이 바닥에 떨어진다. 시작 시점에는 여전히 콤보스킬이 없다
- 첫 문지기 보상은 활/방패와 활/방패 기본 콤보스킬 1개씩이다. 총 4개의 드랍 오브젝트로 떨어지고, 이 시점에는 보조형스킬을 주지 않는다
- 보조형스킬은 이후 보스/파밍 드랍으로 얻고, 마을 NPC와 대화해 콤보스킬 슬롯에 장착한다
- 시스템이 진행 중 강제로 게임을 멈추고 전체 화면 안내를 띄우지 않는다
- 보스 보상은 바닥 아이템으로 떨어지고, 플레이어가 가까이 가면 자동으로 획득된다

## 6. 장르 및 조작

- 장르: 2D 탑다운 액션 로그라이트. 방을 옮겨 다니며 정리하는 구조
- 목표 플랫폼: 데스크톱 브라우저 우선, 모바일 브라우저 최소 대응
- 화면: 브라우저 전체 화면에 가까운 캔버스. 논리 해상도 1280×720
- **방은 화면보다 크다.** 흐린 입구 1900×1150, 첫 문지기 2000×1250, 이후 전투 방 2400×1400, 마을 1600×900. 카메라가 플레이어를 따라간다
- HUD는 화면에 고정되고, 화면 밖의 적과 출구는 가장자리 화살표로 표시된다

시점을 탑다운으로 정한 근거는 두 가지다.

첫째, 원안 두 파일에 카메라 시점 명시가 없고 유일한 단서가 `02. 전투시스템 초안.xlsx`의 `WASD / 좌클릭=왼손, 우클릭=오른손`이다. WASD는 4방향 자유 이동이므로 횡스크롤이 아니라 평면 이동을 전제한다.

둘째, 이 게임의 차별점인 보조능력 조합이 열린 평면에서 가장 잘 드러난다. 다중투사체·갈래·연쇄는 사방으로 퍼질 공간이 있어야 형태가 보이고, 지대는 바닥에 붙지 않아야 위치 선택이 의미를 갖는다.

이동과 조준이 독립적이어야 하는 설계이므로 웹(키보드+마우스)을 목표 플랫폼으로 삼는다.

| 입력 | 동작 |
| --- | --- |
| WASD | 이동 |
| 마우스 이동 | 조준 |
| 좌클릭 | 왼손 무기 공격 |
| 우클릭 **또는 Shift** | 오른손 무기 공격 |
| Space | 대시 |
| R 홀드 | 해금 후 전투 중 무기 교체 링 메뉴 |
| F | 드랍 획득 / 마을 NPC 대화 |

### 방 구조

한 화면에 다 들어오는 아레나에서 버티는 구조는 디펜스에 가까웠다. 방을 옮겨 다니는 구조로 바꿨다.

- 방에 들어서면 왼쪽에서 시작하고 적이 흩어져 있다
- 적을 모두 정리하면 오른쪽 벽의 출구가 열린다
- 출구까지 걸어가면 다음 방 또는 마을 방으로 넘어간다
- 마을 방에서는 NPC에게 가까이 가서 `F`로 실체화 장비 설정 패널을 연다
- 마지막 보스 방도 보스 드랍을 직접 주운 뒤 결과로 넘어간다

참고한 것은 아이작의 방 이동이되 **방 크기를 화면보다 크게** 잡았다. 한 화면에 다 보이면 다시 아레나가 되기 때문이다. 다만 절차적 생성·분기 맵·파밍·상점은 넣지 않는다. 예선 범위에서 검증할 수 없다.

방이 화면보다 크므로 위치를 알려주는 장치를 둘 둔다.

- **가장자리 화살표** — 화면 밖 적과 출구의 *방향*
- **미니맵** — 방 전체에서의 *거리와 분포*. 우상단에 방 비율대로 그린다

화살표만으로는 남은 적이 몇 걸음 거리인지 알 수 없어, 넓은 방을 가로지르는 판단을 할 수 없었다.

### 배경 서술

기획 방침은 프롬소프트웨어식이다. 컷신이나 대사로 설명하지 않는다.

방마다 작은 표식을 두 개 놓아두고, **다가가면 한두 문장이 뜬다.** 멀어지면 사라진다. 읽었는지 게임이 기록하지 않고, **하나도 읽지 않아도 끝까지 진행된다.**

내용은 적이 주인공의 과거와 얽혀 있다는 것과 여기가 정상적인 장소가 아니라는 것까지만 흘린다. **엔딩의 반전은 문장으로 말하지 않는다.** 텍스트는 `src/data/lore.ts`에 데이터로 있어 문장만 고치면 된다.

이 방식을 고른 이유는 방침에 맞을 뿐 아니라 비용이 가장 낮기 때문이다. 컷신·대사·연출 없이 텍스트 8줄과 근접 판정 하나로 끝난다.

## 7. 무기 4종

공격 아키타입이 서로 겹치지 않는 4종만 구현한다. 엔진이 범용이라는 것을 증명하기 위한 선택이다.

| 무기 | 아키타입 | 기본 공격 | 넉백 | 상태이상 | 콤보 발동 스킬 |
| --- | --- | --- | --- | --- | --- |
| 검 | 근접 지속딜 | 베기 (전방 스윙) | 18 | 벌어진 상처 | 멸검 (지대) |
| 활 | 원거리 약점 | 화살 사격 (투사체) | - | 약점 노출 | 연사 (투사체 5) |
| 비전 | 마법 피해 | 비전 탄 (투사체) | - | 낙인 | 비전단검 (투사체 6) |
| 방패 | 방어·제어 | 밀치기 (근접, 낮은 피해) | 115 | 균열 | 균열 파동 (지대, 낮은 피해) |

망치와 클로는 제외한다. 망치는 검과, 클로는 검·활과 아키타입이 겹쳐 늘려도 새로운 것을 보여주지 못한다.

무기 차이를 수치가 아니라 동작으로 드러내기 위해 넉백을 둔다. 방패의 밀치기는 검의 6배 이상 밀어내며, 벽까지 밀린 적은 추가 피해와 확정 기절을 받는다. 휘두르는 연출도 다르다. 검은 110ms로 짧게 스치고, 방패는 240ms 동안 범위가 커지며 밀고 나간다.

방패는 다른 무기보다 피해가 확실히 낮은 대신, 방패 공격을 실제로 사용할 때 체력보다 먼저 소모되는 별도 에너지 보호막을 제공한다. 단순히 R링 후보나 양손 로드아웃에 넣어둔 것만으로는 보호막이 켜지지 않는다. 보호막은 무기를 바꿨다가 다시 들어도 자동으로 차지 않고, 방을 클리어한 뒤 다음 스테이지에 들어갈 때만 초기화된다. 방패 공격으로 보호가 열린 짧은 시간 동안에는 받는 피해도 45%로 줄어, 보스에게 CC가 통하지 않는 상황에서도 막으며 버티는 역할을 갖는다.

### 상태이상 수치 (02 파일 기준)

| 상태 | 부여 조건 | 효과 |
| --- | --- | --- |
| 벌어진 상처 | 검 명중 시 1스택 | 5스택 도달 시 추가 피해 후 초기화, 5초 지속 |
| 약점 노출 | 활 명중 시 30% | 받는 피해 10% 증가, 5초 지속 |
| 낙인 | 비전 명중 시 7% | 낙인 대상 공격 시 제거되며 비전 피해 25% 증폭 (5초) |
| 균열 | 방패 명중 시 10% | 즉시 기절 2초, 이후 7초간 재기절 불가 |

보스는 기본적으로 CC기에 면역이다. 넉백, 기절, 이동 방해처럼 자세나 동작 속도를 흔드는 효과는 보스에게 적용되지 않는다. 단, 보조2형 시너지 스킬이 `bossCc` 성격을 제공하는 경우에는 해당 스킬에 한해 보스 CC 적용을 허용한다. 문지기가 자기 돌진 중 벽에 부딪혀 잠시 멈추는 것은 플레이어 CC가 아니라 보스 패턴의 약점이므로 유지한다.

### 교차 반응

**상처를 남긴 무기가 아닌 다른 무기로 때리면 쌓인 상처를 소모하고 스택당 15의 추가 피해를 준다.**

상처 폭발은 5스택이 필요한데 검 피해 46 기준 사냥개(체력 52)와 몰이꾼(60)은 2타에 죽어 **규칙이 구조적으로 발동하지 않는다.** 이 반응이 그 구멍을 메운다. 잡몹 밀도를 올리면서 마리당 체력이 더 낮아졌으므로 이 구멍은 오히려 커졌다.

동시에 무기를 두 개 고르는 선택에 의미를 만든다. 그전까지 좌/우손은 콤보도 보조능력도 따로였고 서로 아무 상호작용이 없었다.

4스택 소모는 60으로 검 한 대(46)보다 조금 크지만 5스택 폭발(90)보다는 작다. 검이 있다면 한 대 더 때려 터뜨리는 쪽이 여전히 이득이므로, 반응이 폭발을 대체하지 않는다.

상태이상 4종 중 상처에만 교차 반응을 둔 이유는 **상처만 부여 확률이 100%**이기 때문이다. 나머지는 30%·10%·7%라 반복 학습이 어렵다. 다만 이 때문에 검이 필수 픽처럼 느껴질 수 있어, 플레이 테스트에서 확인이 필요하다.

### 적 4종

| 적 | 행동 | 체력 | 역할 |
| --- | --- | --- | --- |
| 사냥개 | 추적 | 52 | 수로 압박한다. 검 2타에 죽는다 |
| 껍데기 | 추적 | 260 | 느리지만 단단해 진행을 끊는다 |
| 몰이꾼 | 원거리 | 60 | 선호 거리를 유지하며 사격한다 |
| 문지기 | 추적 | 1600 | 보스. 반지름이 사냥개의 3.4배다 |

몰이꾼을 넣은 이유는 플레이어 이동 속도(300, 대시 900)가 근접 적(96)의 3배 이상이라, 추적형만 있으면 계속 도망치는 것만으로 한 대도 맞지 않기 때문이다. 거리를 벌리는 행동에 대가를 만든다. 2번 방부터 등장한다.

### 잡몹 밀도

기획 방향은 **"잡몹 수량이 엄청 많고 걔네는 그냥 다 쉽게 썰면서 나아간다"**이다.
그래서 기준을 방의 총 체력이 아니라 **처치 횟수**로 잡았다.

`src/game/rooms.ts` 기준 현재 배치다.

| 순서 | 방 | 구성 | 처치 수 |
| --- | --- | --- | --- |
| 1 | 흐린 입구 | 사냥개 6 | 6 |
| 2 | 첫 문지기 | 문지기 1, 사냥개 4 | 5 |
| - | 마을 | 전투 없음 | - |
| 3 | 해금 시험장 | 사냥개 20, 몰이꾼 4, 껍데기 2 | 26 |
| 4 | 파편 회랑 | 사냥개 18, 몰이꾼 5, 껍데기 3 | 26 |
| 5 | 무너진 문 | 무너진 문 1, 사냥개 14, 몰이꾼 4, 껍데기 2 | 21 |

1·2번 방은 조작과 첫 보스를 익히는 구간이라 일부러 적게 둔다. 밀도는 마을 이후부터 올린다.
다만 첫 문지기는 체력 70%/35%에서 사냥개를 소환하므로, 실제로 상대하는 수는 배치보다 많다.

방의 총 체력은 거의 그대로 두고 마리당 체력만 낮췄다. 같은 시간에 죽는 것이 두 배 이상 많아진다.

수를 늘려도 받는 피해가 그만큼 늘지는 않는다. 피격 후 0.6초 무적이 있어 **들어오는 피해에 상한이 있고, 그 상한은 적이 몇 마리든 같기 때문이다.** 그래서 밀도만 올리면 오히려 쉬워진다. 사냥개 접촉 피해를 8에서 11로 올려 상쇄했다.

## 8. 3개 서브시스템과 보조형스킬

보조형스킬은 보스 드랍으로 얻은 뒤 마을에서 콤보스킬에 장착되어 성질을 바꾼다.

### 8.1 투사체 조합 엔진 (7종)

투사체의 생성·분열·충돌 이후 거동을 조합 가능한 규칙으로 처리한다.

| 보조능력 | 효과 |
| --- | --- |
| 다중투사체 | 투사체 수 +2, 투사체 피해 20% 감소 |
| 갈래 | 갈라지는 투사체 수 +3, 투사체 피해 40% 감소 |
| 관통 | 관통 횟수 2회 |
| 상위 관통 | 모든 대상 관통 |
| 연쇄 | 연쇄 +2, 연쇄마다 피해 20% 감소, 동일 대상 2회까지 |
| 튕겨쏘기 | 지형 충돌 후 1회 추가 튕김 |
| 투사체 속도 증가 | 속도 50% 증가, 피해 20% 증가 |

우선순위 규칙은 원안을 따른다: `관통 > 연쇄 > 갈래 > 튕겨쏘기`

다발 투사체는 발당 피해에 전역 보정을 받는다. 투사체 수가 늘면 총합 피해는 1발보다 강해지지만, 보스처럼 큰 대상에게 여러 발이 동시에 맞아도 투사체 수만큼 선형으로 폭증하지 않는다. 현재 총합 배율은 `투사체 수^0.6`이다.

### 8.2 지대 엔진 (4종)

지대는 위치·반경·지속시간·틱 간격·피해 타입을 갖는 엔티티다. 콤보 발동 스킬 중 멸검과 균열 파동이 지대를 생성한다.

| 보조능력 | 효과 |
| --- | --- |
| 폭발하는 지대 | 생성 2초 후 폭발, 물리 피해의 40%를 화염으로 전환, 점화 지대 2초 생성 |
| 찌릿거리는 지대 | 감전 지대로 전환, 지속시간 +1초, 물리 피해 50%를 번개로 전환 |
| 끌어내리는 지대 | 냉각 지대로 전환, 지속시간 +2초, 물리 피해 50%를 냉기로 전환 |
| 지진 | 효과 범위 100% 증가, 지속피해 간격 50% 가속, 피해 20% 감소, 적 이동 방해 |

### 8.3 범용 수정자 파이프라인 (4종)

원안의 계산 규칙을 그대로 구현한다: **증가/감소를 먼저 합산한 뒤 증폭/감폭을 곱연산으로 적용한다. 증가·증폭은 곱하기, 감소·감폭은 나누기.**

| 보조능력 | 효과 |
| --- | --- |
| 부귀 | 보조 대상 스킬 피해 25% 증가 |
| 과감한 결단 | 콤보 지속시간 100% 증폭, 콤보 획득 1.5배, 피해 10% 증가 |
| 추가 중첩 | 중첩 가능 횟수 +1, 피해 10% 감소 |
| 지속되는 평정 | 지속시간 50% 증폭 |

원안의 `과감한 결단`은 콤보를 50% 확률로 2배 획득한다. 확률 대신 결정적인 1.5배로 구현했다. 3-5분짜리 한 판에서 콤보 획득이 운에 좌우되면 발동 스킬을 한 번도 못 보는 판이 생길 수 있어, 기댓값은 유지하되 분산을 없앴다.

## 9. 콤보 시스템

- 기본 공격이 적에게 명중할 때마다 콤보 +1. 목표는 5
- 콤보스킬을 아직 보유하지 않은 초반에는 콤보가 차도 기본 공격만 나간다
- 콤보스킬을 보유한 뒤 목표에 도달하면, 콤보가 유지되는 동안 해당 손 무기는 기본 공격 대신 장착된 콤보스킬 형태로 공격한다
- 콤보스킬 명중은 콤보 지속시간을 갱신한다. 계속 맞히면 유지되고 놓치면 5초 뒤 끊긴다
- 콤보 배지는 손마다 화면에 고정 표시되며, 미보유 콤보스킬은 `잠김`으로 표시된다
- 무기별로 콤보가 따로 쌓인다. 좌/우손을 번갈아 쓰면 각각 채워야 한다

명중 단위로 오르므로 근접 무기가 여러 적을 한 번에 쓸면 콤보가 그만큼 오른다. 의도한 보상인지 스윙 1회당 1로 바꿀지는 플레이 테스트에서 판단한다.

### 콤보를 지속 상태로 둔 이유

원안은 `기본 공격 n콤보 **이상 시** 부여된 스킬로 **전환**됨`과 `콤보는 기본 지속시간 n초`라고 적고 있다. `이상 시`는 조건이고 `전환`은 모드이며 콤보 자체에 지속시간이 있으므로, **콤보가 살아 있는 동안 발동 상태가 유지되는 구조**다. 한 번 쓰고 사라지면 `이상 시`와 `지속시간` 둘 다 의미가 없어진다.

이전 빌드에는 기본 공격과 콤보스킬이 병행 발동되는 임시 해석이 있었지만 폐기했다. 현재 예선 구조는 기획 의도대로 **콤보스킬이 기본 공격을 대체**한다. 대신 대체가 손해가 되지 않도록 콤보스킬 피해와 발동 간격을 별도로 조정했다. 지대형 콤보스킬은 중첩 피해 폭증을 막기 위해 무기별 `comboInterval`을 사용한다.

## 10. 데이터 스키마 방향

보조능력과 무기는 코드가 아니라 데이터로 정의한다. 이 구조 자체가 제출 문서의 핵심 소재다.

```ts
type Support = {
  id: string;
  name: string;
  tags: Tag[];              // 투사체 / 지대 / 지속시간 / 중첩 / 공격 ...
  requires: Tag[];          // 이 태그를 모두 가진 스킬에만 장착 가능
  modifiers: Modifier[];    // { stat, mode: 'flat'|'increase'|'reduce'|'more'|'less', value }
  behaviors?: Behavior[];   // { kind: 'pierce'|'chain'|'fork'|'convert'|..., params }
  description: string;      // 선택 화면에 그대로 표시된다
};
```

태그 시스템이 장착 가능 여부를 결정하므로, 잘못된 조합이 애초에 만들어지지 않는다. 이것이 QA 표면적을 줄이는 핵심 장치다.

## 12. 기술 스택

- **Vite + TypeScript**
- **Phaser 4** (4.2.1)
- GitHub Pages 배포
- 제출 문서는 Markdown 작성 후 PDF 변환

Phaser를 선택한 이유는 이 게임이 투사체와 지대 엔티티를 대량으로 생성하기 때문이다. 충돌 처리와 스프라이트 풀링을 그대로 쓸 수 있어, 순수 Canvas로 갈 때 직접 만들어야 하는 비용이 사라진다. 번들은 빌드 기준 1.38MB(gzip 359KB)로 GitHub Pages에 문제되지 않는다.

Phaser 4는 렌더러가 새로 쓰인 메이저 버전이라 참고 자료가 3보다 적다. 다만 투사체·지대·근접을 모두 올린 상태에서 렌더링 문제가 나오지 않았고, Phaser에 직접 의존하는 코드는 `main.ts`와 씬 3개뿐이라 필요하면 교체 비용도 작다.

`engine/` 아래 전투 로직은 Phaser를 import하지 않는다. 렌더링과 분리해 두어 규칙을 테스트로 고정할 수 있고, 표현 방식이 바뀌어도 살아남는다.
