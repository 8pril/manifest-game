# 플레이 테스트 요청

작성일: 2026-07-26  
대상: 기획 담당

플레이 링크: **https://8pril.github.io/nan2026-game/**

설치 없이 브라우저에서 바로 실행된다. Chrome 권장.

## 한 판 구조

무기 2개를 고르는 것으로 시작한다. 첫 번째가 왼손(좌클릭), 두 번째가 오른손(우클릭).

```
무기 2종 선택 → 웨이브 1 → 보조능력 3택1
            → 웨이브 2 → 보조능력 3택1
            → 웨이브 3 → 보조능력 3택1
            → 보스 → 승리 / 패배
```

| 입력 | 동작 |
| --- | --- |
| WASD | 이동 |
| 마우스 | 조준 |
| 좌클릭 / 우클릭 | 왼손 / 오른손 무기 |
| Space | 대시 (대시 중 무적, 적을 통과함) |
| 1-4 | 무기·보조능력 선택 |
| R | 재시작 |

기본 공격이 **5번 명중하면** 다음 공격이 그 무기의 발동 스킬로 바뀐다. 화면 아래에 콤보 게이지가 있다.

## 확인할 것

무기 조합은 12가지지만 전부 할 필요는 없다. **3~4가지만** 골라도 충분하다. 근접(검·방패)과 원거리(활·비전)를 섞으면 차이가 잘 드러난다.

1. **한 판 소요 시간.** 목표는 3~5분.
   - **참고:** 자동 검증 봇이 활+비전으로 **43.7초 만에 보스까지 클리어**했다(체력 23 잔존).
     봇은 사람보다 못 싸우는데도 이 정도라, 한 판이 목표 길이의 1/4 수준일 가능성이 높다.
     난이도가 쉬운 것과는 별개다. 봇도 체력 100 중 77을 잃었다. **길이만 짧다.**
     늘린다면 웨이브를 추가하거나 웨이브당 적 수를 늘리는 쪽이지, 적을 더 세게 만드는 쪽이 아니다.
2. **무기 조합별 체감 난이도.** 유독 쉽거나 어려운 조합이 있는지.
   - **참고:** 12개 조합을 봇으로 한 판씩 돌린 결과, 왼손이 활·비전이면 보스까지 갔고
     왼손이 방패면 두 판에서 **50초 동안 처치 0**이었다. 방패는 피해 38에 쿨 420ms로
     초당 피해가 검의 60% 수준인데다, 넉백 115가 적을 사거리 밖으로 밀어내 스스로
     타격 기회를 줄인다. 봇이 뒤로 물러나며 싸워서 과장된 면은 있지만,
     **방패를 주력으로 들었을 때 킬 속도가 나오는지** 확인이 필요하다.
3. **사수(노란 사각형, 웨이브 2부터)가 카이팅을 막는지.** 너무 아픈지, 무시해도 되는지.
4. **상태이상이 눈에 보이는지.** 적 머리 위 색 점에 더해, 규칙이 발동하는 순간에 연출을 넣었다.
   상처 폭발(붉은 링 + `+90`), 낙인 소모(보라 파동 + 플레이어 오라), 벽 충돌(충격 + 흔들림 + `+40`).
   이걸로 무슨 일이 일어났는지 알 수 있는지 봐줄 것.
   - **확인 필요:** 상처 폭발(5스택)은 계산상 추적자와 사수에게는 절대 발동하지 않는다.
     베기 46 피해에 추적자 체력 120이라 3타에 죽어 5스택에 도달하지 못한다.
     중장갑(7타)과 보스(35타)에서만 터진다. 즉 웨이브 1에서는 한 번도 볼 수 없다.
     이대로 "단단한 적을 무너뜨리는 마무리"로 둘지, 아니면 스택 요구치를 낮추거나
     적 체력을 올려 자주 보이게 할지 판단이 필요하다.
5. **콤보 발동 빈도.** 5타가 너무 빠른지 느린지.
   - 참고: 콤보는 **적 하나 맞힐 때마다** 1씩 오른다. 근접 무기로 3마리를 한 번에
     쓸면 콤보가 3 오른다. 그래서 적이 몰린 상황에서는 발동 스킬이 훨씬 자주 터진다.
     이게 의도한 맛인지, 아니면 스윙 1회당 1로 바꿔야 하는지 판단이 필요하다.
   - 콤보가 차면 플레이어 주위에 무기 색 링이 뜬다. 이 표시가 눈에 들어오는지도 봐줄 것.
6. **보스 클리어 가능 여부.** 아직 아무도 승리 화면에 도달하지 못했다. 도달하면 알려줄 것.

## 기록 형식

```
[플레이 1]
무기: 검 + 활
결과: 웨이브 3에서 패배 / 소요 4분 20초
난이도: 웨이브 2까지는 쉬웠는데 사수 3마리부터 급격히 어려움
느낀 점:
```

몇 판이든 이 형식으로 누적하면 된다. 이 기록은 팀원 롤 기술서의 근거 자료로 들어간다.

## 수치 직접 조정

밸런스 수치는 5개 파일에 모여 있다. 코드를 몰라도 숫자만 바꾸면 된다.

| 파일 | 조정 대상 |
| --- | --- |
| `src/game/enemy.ts` | 적 체력·속도·피해·사거리 |
| `src/game/waves.ts` | 웨이브별 적 구성 |
| `src/data/weapons.ts` | 무기 피해·사거리·쿨다운 |
| `src/game/combo.ts` | 콤보 요구치(현재 5)·지속시간 |
| `src/game/run.ts` | 플레이어 체력·무적 시간 |

**바꾼 내용은 직접 커밋한다.** 커밋 기록도 심사 대상이므로 기획 담당 명의로 남는 편이 기술서 작성에 유리하다.

로컬 실행 시 주소 뒤에 `?scene=Play&wave=3`을 붙이면 웨이브 3부터 시작한다. 후반 웨이브만 볼 때 쓴다.

```bash
npm install
npm run dev
# http://localhost:5173/?scene=Play&wave=3
```

## 아트 작업

**아트 생성 전에 `docs/concept-brief.md`를 먼저 채워야 한다.** 원안에 세계관이 없어
프롬프트의 주인공·적·장소 관련 단어를 개발 쪽에서 임시로 지어넣은 상태다. 그대로
생성하면 그 임시 단어가 게임의 비주얼 정체성으로 굳는다.

세계관과 이름이 정해지면 `docs/art-spec.md`의 프롬프트를 다시 쓰고 생성을 시작한다.
생성한 이미지는 `assets-raw/` 폴더에 파일명 그대로 넣고 커밋하면 개발 쪽에서 반영한다.

플레이 테스트와 병행 가능하다. 순서를 정하자면 플레이를 먼저 해보는 쪽이 낫다.
게임이 어떻게 움직이는지 봐야 어떤 그림이 필요한지 감이 잡힌다.

## 알아둘 것

- 승리 화면은 아직 실제 플레이로 확인된 적이 없다
- 사운드와 튜토리얼은 아직 없다. 기본 전투 이펙트는 들어갔지만, 사람이 실제 플레이로 충분히 읽히는지 확인해야 한다
- 진행이 막히는 버그를 만나면 화면과 직전 행동을 함께 알릴 것
