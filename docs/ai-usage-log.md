# AI 활용 기록 로그

이 파일은 최종 제출물인 `AI 활용 기술 문서` 작성을 위한 원천 기록이다.  
AI를 사용한 모든 의사결정, 프롬프트, 결과, 사람의 검토 및 수정 내용을 이곳에 누적한다.

## 기록 원칙

- AI를 사용한 즉시 기록한다.
- 프롬프트는 가능한 한 원문에 가깝게 남긴다.
- AI 결과물을 그대로 사용했는지, 수정했는지, 폐기했는지 명확히 적는다.
- 게임에 반영된 결과와 반영되지 않은 결과를 구분한다.
- 저작권, 라이선스, 외부 출처 관련 내용은 빠뜨리지 않는다.
- 주요 작업이 끝났는데 기록할 내용이 없다고 판단한 경우, 최종 응답에서 그 이유를 명시한다.
- 이 프로젝트의 작업 규칙은 루트의 `AGENTS.md`에도 기록되어 있으며, 작업 종료 전 이 파일 업데이트 여부를 확인한다.

## 단계별 기록 액션

- [ ] AI에게 기존 기획의 핵심 루프 요약을 요청했다.
- [ ] AI가 제안한 스코프 축소안을 검토했다.
- [ ] 채택한 기능과 제외한 기능을 기록했다.
- [ ] 사람이 최종 결정한 이유를 기록했다.

기록해야 할 내용:

- 기획 요약 프롬프트
- AI가 제안한 핵심 재미 요소
- 예선 빌드에서 제외한 기능
- 최종 선택 이유

### Phase 1. 프로젝트 세팅

- [ ] 기술 스택 후보 비교에 AI를 사용했다.
- [ ] 선택한 스택과 선택 이유를 기록했다.
- [ ] AI가 생성 또는 제안한 초기 구조를 기록했다.
- [ ] 사람이 수정한 프로젝트 구조를 기록했다.

기록해야 할 내용:

- Vite, Phaser, Canvas 등 후보 비교

### Phase 2. 핵심 플레이 구현

- [ ] 핵심 게임 루프 구현에 AI를 사용했다.

기록해야 할 내용:

- 플레이어 조작 구현
- 전투/점수/자원/턴/웨이브 로직
- 승리/패배 조건
- 버그 원인과 수정 이유

### Phase 3. 콘텐츠 채우기

- [ ] 무기, 상태이상, 콤보 발동 스킬, 보조능력 데이터 작성에 AI를 사용했다.
- [ ] 태그 기반 장착 가능 여부와 조합 규칙 설계에 AI를 사용했다.
- [ ] 사람이 편집, 검증, 밸런싱한 내용을 기록했다.
- [ ] 최종 게임에 반영된 AI 코딩 에이전트 활용 사례를 정리했다.

기록해야 할 내용:

- AI로 만든 무기 데이터, 보조능력 데이터, 적 패턴, 웨이브, 밸런스 초안

- 결과물 중 채택/수정/폐기 항목

### Phase 4. 폴리싱 및 안정화

- [ ] UI 문구, 튜토리얼, 밸런스 조정에 AI를 사용했다.

**1차 시도 (Codex) — 효과 없음**

- 처음에는 `devicePixelRatio` 기반 `resolution` 옵션이 이상적이라고 판단했으나, Phaser 4 `GameConfig`에 해당 옵션이 없어 타입 검사에서 실패해 되돌림
- 논리 해상도를 1920×1080으로 올리면 게임장 크기와 이동 속도 체감이 달라질 수 있다고 보아 보류하고, 대신 `pixelArt: false`, `antialias: true`, `antialiasGL: true`, `roundPixels: false`를 최상위에 명시하는 보수적 조치를 적용
- 빌드와 테스트는 통과했고 선명도 보강으로 보고되었다

**검증 (Claude Code) — 1차 시도가 무효임을 확인**

- 사람이 "적절한 수정이야?"라고 물어, 주장을 검증하기 위해 CDP로 캔버스 실측
- DPR 2 환경에서 백버퍼 1280×720이 물리 픽셀 2052×1154로 표시되어 **확대 배율 1.6배**. 이것이 흐릿함의 원인이었다
- 추가된 네 옵션은 Phaser가 백버퍼 **안에** 그리는 방식을 정할 뿐, 브라우저가 그 버퍼를 화면으로 늘릴 때의 보간에 관여하지 않는다. 게다가 넷 다 Phaser 기본값이고 `pixelArt`와 `antialias`는 이미 `render: {}`에 있었다. 즉 동작이 전혀 바뀌지 않는 중복 설정이었다
- 무해하지만 무효였고, 보고 내용이 실제 효과보다 과장되어 있었다

**2차 시도 (Claude Code) — 실제 해결**

- 흐릿함은 백버퍼 크기 문제이므로 백버퍼를 키우는 것 외에 방법이 없다. 다만 논리 해상도를 그대로 1920×1080으로 올리면 모든 위치·속도·크기 상수가 함께 흔들린다는 1차 판단은 옳았다
- 그래서 **월드 좌표계와 캔버스 크기를 분리**했다. `GAME_WIDTH/HEIGHT`는 1280×720 그대로 두고, `CANVAS_WIDTH/HEIGHT`를 `RENDER_SCALE`(1.5)배로 잡아 백버퍼만 1920×1080으로 키웠다. 각 씬에서 카메라를 같은 배율로 확대하고 스크롤을 보정해, 화면에 보이는 월드 영역은 정확히 1280×720으로 유지된다

- 순서에 대한 판단: Codex는 "아트 생성 전에 하는 게 맞다"고 했고 결론은 같지만 근거는 달랐다. `docs/art-spec.md`의 14장은 캐릭터·투사체·지대·바닥이고 이펙트 에셋이 없으므로 두 작업은 서로 막지 않는다. 지금 해야 하는 실제 이유는 **플레이 테스트 인계** 때문이다. 상태 시스템이 보이지 않는 상태로 넘기면 기획 담당이 그것을 인지하지 못한 채 평가하게 되어, 가장 희소한 자원인 사람의 플레이 시간에서 얻는 정보가 줄어든다
- 데미지 숫자 범위 조정: Codex는 데미지 숫자를 제안했으나 모든 타격에 띄우면 적 12마리에 다중투사체까지 붙었을 때 화면이 숫자로 덮인다. **규칙 때문에 추가로 들어간 피해에만** 띄우도록 좁혔다(상처 폭발 +90, 벽 충돌 +40). "왜 갑자기 크게 들어갔지"에 답하는 것이 목적이므로 그 순간에만 정보가 붙으면 된다
- 수정한 내용: `src/effects.ts`를 만들어 링 확산, 플래시, 떠오르는 숫자, 충격(링 + 약한 화면 흔들림)을 모았다. 전부 Phaser 도형과 트윈이라 아트 에셋에 의존하지 않으며, 나중에 스프라이트가 들어와도 이 파일만 고치면 된다. 상처 폭발·낙인 소모·벽 충돌 세 지점에 배선하고, 비전 흐름이 걸린 동안 플레이어를 감싸는 오라를 추가해 남은 시간에 따라 옅어지게 했다. 카메라 확대가 걸려 있어 화면 흔들림은 약하게만(0.003, 120ms) 넣었다
- **검증 중 발견한 설계 문제**: 봇으로 상처 폭발을 재현하려다 실패했고, 계산해보니 구조적으로 불가능한 조합이 있었다. 베기 피해 46 기준으로 추적자(체력 120)는 3타, 사수(90)는 2타에 죽어 **5스택에 도달하기 전에 죽는다.** 중장갑(7타)과 보스(35타)에서만 발동한다. 즉 웨이브 1에서는 상처 폭발을 한 번도 볼 수 없다. 원안의 5스택 규칙은 그대로지만 적 체력과 무기 피해는 AI가 정한 값이므로, 이 불일치는 AI가 만든 것이다
- 판단 보류: 이대로 "단단한 적을 무너뜨리는 마무리"로 두는 것도 설계로서 말이 되므로 수치를 임의로 바꾸지 않고 `docs/playtest-brief.md`에 확인 항목으로 넘겼다
- 검증의 한계: 빌드와 테스트는 통과했고 콘솔 에러도 없으나, **폭발·충격 연출이 실제로 그려지는 프레임을 스크린샷으로 잡지 못했다.** 헤드리스 봇이 조준을 고정 좌표로 하고 이동하지 않아 보스전에서 10초 내에 죽는다. 연출을 띄우는 조건은 피해량을 바꾸는 조건과 동일하고 그 동작은 확인되었으므로 로직은 맞지만, 표시 여부는 사람이 확인해야 한다
- 게임/문서 반영 여부: 코드와 문서 모두에 반영
- 관련 파일: `src/effects.ts`, `src/scenes/PlayScene.ts`, `docs/playtest-brief.md`
- 남은 이슈: 연출 육안 확인, 상처 폭발 발동 조건 판단

### 2026-07-28 - 검증 드라이버 개선 (상태 인식 + 이벤트 촬영)

- 단계: M6 폴리싱 (검증 도구)
- 사용 AI 도구: Claude Code (Opus 5)
- 목적: 헤드리스 검증이 계속 실패하던 원인을 제거한다
- 입력 프롬프트 / 지시: "봇이 왜 이동을 안해?", "조준 정책도 지금 다듬는게 나은가?"
- AI가 잘못 말했던 것: 연출 프레임을 못 잡은 이유를 "봇이 이동을 안 해서"라고 설명했으나 부정확했다. 드라이버가 두 개였고 그중 `kite.mjs`는 이동을 했다. 이동하는 쪽은 고정 화면 좌표로 쏘느라 100초 동안 처치 0이었고, 이동하지 않는 쪽은 적이 알아서 붙어 명중은 하지만 금방 죽었다. **둘 다 쓸 수 없어서 덜 나쁜 쪽을 골랐던 것이고, 진짜 원인은 봇이 적 위치를 모른다는 것이었다**
- 수정한 내용:
  1. `src/debug.ts` 신설. 개발 빌드에서만 `window.__debug`에 플레이어·적 위치, 체력, 콤보, 좌표 변환값을 노출한다. `import.meta.env.DEV`는 프로덕션 빌드에서 `false`로 치환되고 죽은 분기가 제거되므로 제출 빌드에는 들어가지 않는다. 실제로 빌드 산출물에서 `__debug` 검색 결과가 0건임을 확인했다
  2. 새 드라이버 `smart.mjs`. 상태를 읽어 가장 단단한(또는 가장 가까운) 적을 조준하면서 동시에 가장 가까운 적 반대 방향으로 물러난다. 무기 선택 화면에서 시작해 지정한 무기를 고르는 것도 지원한다
  3. **규칙 발동 횟수를 카운터로 노출**했다. 연출이 340ms라 주기적 촬영으로는 계속 놓쳤는데, 드라이버가 카운터 증가를 감지한 즉시 촬영하도록 바꿔 확정적으로 잡을 수 있게 되었다
- 결과: 웨이브 2 기준 생존 10초·처치 0~4에서 **40초·처치 7**로 개선. 상처 폭발(보스, 붉은 링 + `+90`)과 벽 충돌(흰 충격 링 + `+40` + 기절) 프레임을 모두 스크린샷으로 확보했다. 낙인 소모는 부여 확률이 7%라 이번 실행에서는 발생하지 않았다
- 조준 정책 튜닝은 하지 않기로 함: 봇을 더 잘 싸우게 만드는 목적은 사실상 보스 클리어(승리 화면 확인) 하나인데, 승리 전이는 이미 단위 테스트로 검증되어 있고 화면 구조는 패배 화면과 같다. 반대로 봇이 보스를 못 깬다는 사실은 밸런스 정보가 되지 못한다. 봇은 사람보다 훨씬 못하는 플레이어이므로, **"사람이 깰 수 있는가"는 기획 담당의 플레이 테스트가 답할 질문**이다. 봇은 밸런스 판단 도구가 아니라 검증 도구로 쓴다
- 게임/문서 반영 여부: 코드에 반영. 드라이버는 저장소 밖 작업 디렉터리에 둔다
- 관련 파일: `src/debug.ts`, `src/vite-env.d.ts`, `src/scenes/PlayScene.ts`
- 남은 이슈: 무기 조합 12쌍 × 무작위 보조능력으로 여러 판을 돌려 콘솔 에러와 진행 불가 상태를 자동 탐지하는 스모크 런. "재미있는가"는 사람 몫이지만 "깨지는가"는 봇이 더 잘한다

### 2026-07-29 - 전투 문구 표기 수정 (부호 오용)

  - **처치 연출 — 지금 구현.** 적이 그냥 사라졌다. 처치는 자주 일어나는 보상 순간인데 아무것도 남지 않았고, 30-60초 영상에도 직접 영향이 있다
  - **히트스톱 — 보류.** 값어치는 크지만 적 12마리에 다중투사체까지 붙으면 초당 수십 번 명중하므로 매번 멈추면 화면이 덜덜거린다. 무거운 타격에만 걸어야 하는데 "어느 정도가 무거운가"는 손맛 판단이라 사람이 쳐본 뒤에 정해야 한다. 지금 넣으면 추측으로 튜닝하는 것이 된다
  - **사운드 — 별도 트랙.** 코드 작업이 아니라 아트와 같은 에셋 작업이다. 생성하거나 구해야 하고 제출물 4번이 출처와 라이선스를 요구한다. `docs/art-spec.md`에 항목을 추가해 세계관 확정 후 아트와 함께 진행하도록 했다. 같은 노력 대비 체감 변화가 가장 큰 항목이므로 우선순위에서 바닥 타일보다 앞에 두었다
- 수정한 내용: `effects.ts`에 `hitSpark`(짧고 작은 불꽃)와 `deathBurst`(링 + 파편 5개)를 추가하고 `resolveHit`, `damageEnemy`에 배선했다. `hitSpark`는 초당 수십 번 발생할 수 있으므로 130ms에 반경 7로 작게 잡았다. 크게 만들면 다중투사체 빌드에서 화면이 뒤덮인다
- 사운드 스펙에 특기한 제약: `sfx-hit`은 초당 수십 번 날 수 있으므로 짧고 건조해야 한다. 나머지는 드물게 나므로 존재감이 있어도 된다. 무료 음원을 가져오는 경우에도 출처·링크·라이선스 종류를 남겨야 하며 누락은 실격 사유가 될 수 있다
- 검증: 웨이브 2에서 처치 연출(링 + 파편)이 표시되는 프레임을 스크린샷으로 확보. 타격 불꽃은 짧아 화면을 어지럽히지 않는 것을 확인

### 2026-07-29 - 트랙패드 우클릭 문제 대응 (기획자 버그 리포트)

- 단계: M6 폴리싱
- 사용 AI 도구: Claude Code (Opus 5)
- 목적: 노트북 트랙패드에서 오른손 무기를 쓸 수 없는 문제 해결
- 입력 프롬프트 / 지시: 기획 담당 코멘트 - "트랙패드로 플레이할때는 우클릭이 안돼"
- 문제의 성격: 오른손 무기를 우클릭에만 묶어두면 트랙패드 사용자가 쓸 수단이 없다. 왼손이 WASD에 묶여 있어 다른 손으로 보조할 수도 없다
- **원인은 특정하지 못했다.** AI에게는 실제 트랙패드를 재현할 수단이 없다. 합성 우클릭 이벤트(`buttons=2`)로 검증한 결과 오른손 무기가 정상 발동했고, 수정 전 코드의 `rightButtonDown()` 검사도 같은 이벤트에서 참이 되므로 **수정 전에도 코드 경로 자체는 동작했을 가능성이 높다.** 즉 문제는 트랙패드 → OS → 브라우저 구간일 수 있으며(예: macOS 보조 클릭 설정이 모서리 클릭으로 되어 있는 경우), 그 구간은 검증 범위 밖이다
- AI가 성급했던 부분: 처음 보고에서 "두 손가락 탭이 켜져 있어도 액션 게임에서 반복은 불가능하다"고 단정했으나 **테스트한 적이 없는 사용성 추측이었다.** 사람이 "지금도 그래?"라고 되물어 확인 범위를 다시 따지면서 드러났다. 검증할 수 없는 것을 사실처럼 말하지 않도록 이 항목을 정정한다
- 수정한 내용:
  1. 감지를 견고하게: `pointer.rightButtonDown()`만 보던 것을 `|| pointer.button === 2`로 보강했다. 브라우저나 입력 장치에 따라 버튼 상태와 이벤트 버튼 번호 중 한쪽만 채워질 수 있다. **다만 이 변경이 실제로 무언가를 고쳤는지는 확인되지 않았다.** 무해하지만 효과 없는 변경일 수 있다
  2. **Shift를 오른손 무기 대체 입력으로 추가.** 왼손이 WASD에 있으므로 새끼손가락으로 닿는 Shift가 가장 자연스럽다. 우클릭도 그대로 동작한다
- 검증: 클릭 없이 마우스만 이동시켜 조준한 뒤 Shift만 10회 눌렀을 때, 오른손 콤보만 0에서 증가하고 왼손 콤보는 0으로 유지되는 것을 디버그 상태로 확인했다. 합성 우클릭 10회로도 같은 방식으로 확인했다(오른손 콤보 0→4). **실제 트랙패드 동작은 확인하지 못했으며 기획 담당의 재확인이 필요하다**
- 반영 범위: 게임 내 안내 문구, `README.md`, `docs/game-scope.md`, `docs/playtest-brief.md`의 조작표를 모두 갱신
- AI가 놓친 부분: 조작 체계를 설계할 때 데스크톱 마우스만 가정했다. `docs/game-scope.md`에 `데스크톱 브라우저 우선`이라고 적어두었지만, 데스크톱 브라우저를 노트북에서 여는 경우를 고려하지 않았다. 심사자도 노트북으로 열 가능성이 높다
- 게임/문서 반영 여부: 코드와 문서 모두에 반영
- 관련 파일: `src/scenes/PlayScene.ts`, `README.md`, `docs/game-scope.md`, `docs/playtest-brief.md`
- 남은 이슈: 없음

### 2026-07-29 - 보조능력 선택지 집중 (와우포인트 논의)

- 단계: M6 폴리싱
- 사용 AI 도구: Codex(제안) → Claude Code (Opus 5, 판단·구현)
- 목적: 한 판에서 눈에 띄는 순간을 만든다
- 입력 프롬프트 / 지시: 코덱스의 교차 반응 제안에 대해 "어떻게 생각해?", 이후 "그래"
- Codex의 제안: 상태이상에 **교차 반응**을 도입한다. 상태는 단독으로도 터지지만 다른 무기로 반응시키면 더 크게 터지는 구조. 상처 + 비전 타격, 약점 노출 + 상처 폭발, 균열 + 벽 충돌, 낙인 + 활/검 등 조합별 반응을 만든다
- 채택하지 않은 이유:
  1. **QA 표면적**: 상태 4종 × 무기 4종에서 자기 자신을 빼면 교차 조합이 12가지다. 이미 무기 12쌍 × 보조능력 15종을 안고 있는데 곱셈을 하나 더 얹는 셈이며, 스코프 상한을 정할 때 피하려던 형태가 정확히 이것이다
  2. **발견 가능성**: 원신 계열이 반응 시스템을 수십 시간에 걸쳐 가르치는 데 반해 심사자는 3-5분만 플레이한다. 12가지를 만들어도 한두 번 우연히 터지고 지나가면 만든 쪽만 아는 시스템이 된다
  3. **일정**: 기능 동결까지 7일인데 기획 담당은 아직 한 판도 플레이하지 않았고, 세계관·아트·사운드가 시작 전이며 제출 문서 3종이 백지다. 지금 새 시스템을 얹으면 플레이 테스트가 움직이는 표적을 상대하게 된다
- 다만 Codex의 진단은 옳았고 AI가 놓쳤던 부분이다: **무기 2개를 고르는 선택이 사실상 의미가 없다.** 좌/우손이 콤보도 보조능력도 따로이고 상호작용이 없어, 게임의 첫 화면에서 하는 선택이 "공격 방식 두 개를 각각 쓴다" 이상을 만들지 못한다
- 대신 채택한 것: **이미 보조능력이 붙은 스킬 쪽으로 선택지를 기울인다.** 새 시스템 없이 기존 시스템만으로 볼 만한 장면을 만드는 방법이다. 연사(투사체 5)에 다중투사체와 갈래가 겹치면 7발이 21발로 갈라지는데, 선택 3회에 스킬이 4개라 균등 추첨으로는 잘 모이지 않았다
- 구현: `rollOffer`에 가중 추첨(Efraimidis-Spirakis 방식, `난수^(1/가중치)`)을 적용하고 가중치를 `1 + 이미 붙은 개수 × 2`로 두었다
- **효과를 측정했다.** 400판을 균등 추첨과 가중 추첨으로 각각 시뮬레이션해 비교한 결과, 한 스킬에 2개 이상 몰리는 비율이 **57% → 88%** 로 올랐다. 3개 이상은 양쪽 모두 0%인데 원안대로 스킬당 슬롯이 2개이기 때문이다. 측정값을 회귀 테스트로 고정해, 편향이 사라지면 실패하도록 했다(임계 70%)
- 배운 것: 테스트가 통과한다고 의도한 효과가 났다는 뜻은 아니다. 확률적 변경은 대조군과 비교해 수치로 확인해야 한다. 렌더 선명도 때와 같은 종류의 함정이었다

  2. 방마다 크기를 갖게 했다. 1번 방 1900×1150, 2·3번 방 2400×1400, 보스 방 2000×1250. 화면(1280×720)보다 크므로 카메라가 플레이어를 따라간다
  3. 적을 모두 정리하면 오른쪽 벽의 출구가 열리고, 걸어서 나가면 보조능력을 고른 뒤 다음 방으로 넘어간다. 즉시 전환이 아니라 이동해야 한다
  4. 화면 밖 적과 출구를 가장자리 화살표로 표시. 방이 화면보다 크면 이것이 없을 때 남은 적을 찾아 헤매게 된다
- 카메라 처리에서 걸린 문제: 고DPI 선명도를 위해 카메라 줌 1.5배를 쓰고 있었는데, `scrollFactor(0)`은 스크롤만 무시할 뿐 확대는 그대로 받는다. 확대가 캔버스 중심 기준이라 화면 좌상단에 해당하는 좌표가 (0,0)이 아니라 (320, 180)으로 밀린다. `screenX`/`screenY` 보정 함수를 만들어 HUD와 오버레이 좌표를 변환했고, 화면 (0,0)과 (1280,720)이 캔버스 모서리에 정확히 대응하는 것을 수치로 확인했다
- 범위에서 뺀 것: 절차적 방 생성, 분기 맵, 파밍·아이템·상점, 미니맵, 토치라이트식 사이드 오브젝티브. 참고는 받되 예선 범위에서 검증할 수 없는 것들이다
- 검증 상태:
  - 확인됨: 방 렌더링, 카메라 추적, HUD 화면 고정, 화면 밖 화살표 표시, 방 크기 반영. 테스트 192개, 콘솔 에러 없음
  - **확인 못 함: 출구가 열리고 다음 방으로 넘어가는 흐름을 스크린샷으로 잡지 못했다.** 방이 커지면서 적이 흩어져 검증 봇이 방 하나를 정리하지 못한다. 반복 시도 중 헤드리스 Chrome이 누적되어 환경이 멎기도 했다. 출구 조건은 방 정리 판정(이미 동작이 확인된 조건)과 단순 사각형 겹침 판정뿐이라 로직은 단순하나, 눈으로는 확인되지 않았다
- 부수 관찰: 방이 커지자 검증 봇의 "무조건 후퇴" 전략이 무력해졌다. 넓은 공간에서는 도망만 다니면 아무도 죽이지 못한다. 반대로 접근하면 포위당한다. 봇 정책을 접근·유지·후퇴로 바꿨으나 여전히 방 1을 넘기지 못한다. **넓은 방이 난이도에 어떤 영향을 주는지는 사람의 플레이로 확인해야 한다**

- 관련 파일: `src/game/rooms.ts`, `src/render.ts`, `src/scenes/PlayScene.ts`, `src/debug.ts`, `docs/game-scope.md`, `docs/playtest-brief.md`

### 2026-07-30 - 방 밖 투사체가 사라지던 버그, 미니맵

#### 원인

**방 구조로 전환하면서 AI가 만든 회귀 버그였다.**

투사체가 사라지는 조건을 화면 크기로 판정하고 있었다.

```ts
projectile.x > GAME_WIDTH + 40 || projectile.y > GAME_HEIGHT + 40  // 1280, 720
```

방이 화면보다 작았을 때는 맞는 판정이었다. 그런데 방을 1900×1150에서 2400×1400까지
키우면서 이 줄을 같이 고치지 않았다. 결과적으로 **플레이어가 x > 1320 또는 y > 760에
있으면 발사한 투사체가 생성된 프레임에 바로 지워졌다.**

방에 들어서면 왼쪽(x≈114)에서 시작하므로 처음에는 정상이다.

**무기에 따라 증상이 다르다는 점이 기획 담당의 표현과 정확히 일치한다.**

적이 쏘는 화살에도 같은 판정이 걸려 있었다. 방 오른쪽·아래쪽에서는 사수가 무해했다.

#### 고친 방법

판정 기준을 화면이 아니라 **현재 방**으로 바꾸고, 그 규칙을 씬이 아니라
엔진(`src/engine/projectile.ts`)으로 옮겼다. 씬 안의 private 메서드로 두면
테스트로 고정할 수 없어 같은 실수가 반복될 수 있다.

- `isOutOfBounds(point, bounds)` 추가, 회귀 테스트 4개
- 그중 하나는 이 버그 자체를 고정한다: 화면 밖이지만 방 안인 좌표에서 `false`여야 한다

#### 검증

헤드리스 브라우저로 같은 판 안에서 대조 측정했다.

| 발사 위치 | 살아남은 투사체 |
| --- | --- |
| x=114, y=575 (예전 화면 범위 안) | 3 |
| x=750, y=1106 (예전 화면 범위 밖) | 3 |

두 값이 같아야 정상이다. 고치기 전이라면 아래 칸은 **반드시 0**이다

1. 드라이버가 숫자 키를 보낼 때 `text` 필드를 빠뜨려 무기 선택이 넘어가지 않았다
2. 측정 중에 소스를 계속 고쳐 Vite HMR이 페이지를 새로고침했고, 게임이 리셋되어
   결과가 뒤죽박죽이었다. **측정 중에는 소스를 건드리면 안 된다**
3. 대조군 없이 한 지점만 재서 0이 나왔을 때, 그것이 버그 때문인지 봇이 죽어서인지
   구분할 수 없었다. 같은 판에서 두 지점을 재고 나서야 결론이 나왔다

넓은 방을 가로지를지 판단할 근거가 없었다.

우상단에 **방 비율 그대로** 그린다. 처음에는 정사각형 틀에 넣었는데,

### 2026-07-30 - 이름 확정, 잡몹 밀도, 보스 크기, 배경 서술

- 단계: M6 폴리싱
- 사용 AI 도구: Claude Code (Opus 5)
- 목적: 미정으로 남아 있던 제목·적 이름을 정하고, 기획 답변 중 비용이 낮은 범위 항목 셋을 반영한다
- 입력 프롬프트 / 지시: "미정인 것들 정하자 추천해줘" → 제목은 "영어가 낫지 않을까?", 범위 3개는 "바로 진행"

#### 이름

AI가 제안하고 사람이 방향(영문)을 정했다.

- **제목 `MANIFEST`** — 원안 첫 시트 이름이 "실체화"이고 그 직역이다. 게임에서 실제로
  하는 행동이면서, **무의식이 만들어낸 것**이라는 뜻이 엔딩 뒤에 뒤늦게 걸린다.
  플레이 중에는 반전을 흘리지 않는다
- 버린 후보: `GAUNTLET`(의미는 가장 잘 맞았으나 1985년 아타리 탑다운 던전 크롤러와
  정면으로 겹친다), `AFTERIMAGE`(2023년 동명 게임), `HOLLOW`(Hollow Knight 연상)
- **적 이름** — 추적자→**사냥개**, 중장갑→**껍데기**, 사수→**몰이꾼**, 보스→**문지기**.
  사냥개와 몰이꾼이 사냥에서의 역할로 짝을 이루어 *플레이어가 사냥감*이라는 인상을 만든다.
  껍데기는 "속이 비어 있다"는 정체를 이름 하나로 말해 설명문이 필요 없다 —
  프롬소프트식 방침에 맞는다. 문지기는 보스가 여러 종이 될 여지를 막지 않는다

#### 잡몹 밀도

기획 방향은 "잡몹 수량이 엄청 많고 걔네는 그냥 다 쉽게 썰면서 나아간다"였다.
기준을 방의 총 체력이 아니라 **처치 횟수**로 잡았다.

| 방 | 처치 수 |
| --- | --- |
| 1번 | 5 → 12 |
| 2번 | 9 → 20 |
| 3번 | 12 → 26 |
| 보스 | 7 → 14 |

방의 총 체력은 거의 그대로 두고 마리당 체력만 낮췄다(사냥개 120→52, 몰이꾼 90→60,
껍데기 320→260). 같은 시간에 죽는 것이 두 배 이상 많아진다.

**설계에서 걸린 것**: 수를 늘려도 받는 피해는 그만큼 늘지 않는다. 피격 후 0.6초 무적이
있어 들어오는 피해에 상한이 있고, **그 상한은 적이 몇 마리든 같다.** 즉 밀도만 올리면
오히려 쉬워진다. 사냥개 접촉 피해를 8에서 11로 올려 상쇄했다.

#### 배경 서술

기획 방침(프롬소프트식)의 최소 구현이다. 방마다 표식 두 개를 놓고 다가가면 한두 문장이
뜬다. 멀어지면 사라지고, 읽었는지 기록하지 않으며, **하나도 읽지 않아도 끝까지 진행된다.**

내용은 적이 주인공의 과거와 얽혀 있다는 것까지만 흘리고 **엔딩의 반전은 문장으로 말하지
않는다.** 텍스트는 `src/data/lore.ts`에 데이터로 두어 문장만 고치면 되게 했다.

첫 확인에서 **글자가 적과 겹쳐 읽히지 않았다.** 어두운 판을 뒤에 깔아 고쳤다.

#### 범위에서 뺀 것과 그 이유

- **보스 다종화·기믹** — 한 판에 보스 방이 하나뿐이라 종류를 늘려도 한 판에서는 하나만
  보인다. 리플레이를 전제한 기능인데 예선에서 그것을 보여줄 시간이 없다
- **보스 드랍 아이템** — **구조적으로 자리가 없다.** 보스를 잡는 순간이 곧 게임의 끝이라
  드랍을 받아도 쓸 방이 없다. 성장 축을 하나 더 만드는 비용은 큰데 플레이에 드러나지 않는다.
  둘 다 "한 판이 더 길고 보스가 여러 번 나오는" 구조를 전제하며, 그것은 본선 범위다

### 2026-07-31 - "두 번째 선택 창에서 클릭이 안 된다" 원인과 수정

- 단계: M6 폴리싱
- 사용 AI 도구: Claude Code (Opus 5)
- 입력 프롬프트 / 지시: 기획 담당 피드백 - "보조능력 창 두번째 나왔을때 클릭이 안돼"

#### 원인 — 이전에 AI가 넣은 수정이 만든 문제

전에 "선택지 연타 문제"를 고치면서 **창이 뜬 뒤 800ms 동안 입력을 막았다.**
그 800ms 동안 누른 것은 큐에 쌓이지 않고 **조용히 사라진다.**

- 첫 번째 창은 선택지를 처음 읽느라 800ms를 넘겨서 멀쩡하다
- 두 번째부터는 뭘 고를지 알고 바로 누르기 때문에 클릭이 통째로 먹히지 않는다

증상이 "두 번째부터"인 이유가 정확히 이것이다.
창이 800ms에 걸쳐 페이드인하는 것도 "아직 안 눌린다"가 아니라 "먹통이다"로 읽히게 했다.

#### 재현

임시로 방의 적을 1마리로 줄인 픽스처를 두고, 창이 뜬 뒤 지연을 바꿔가며 클릭했다.

| 창이 뜬 뒤 클릭까지 | 결과 |
| --- | --- |
| 250ms | ❌ 먹지 않음 |
| 1300ms | ✅ 먹음 |

#### 수정 — 시간이 아니라 단계로 막는다

기획 담당이 예전에 제안했던 방식이다.
> "마우스 인식 못하게 하기보단 스킬 고른 다음에 결정 버튼을 따로 두면 될듯"

카드를 누르면 **고르기만** 하고, 고른 카드를 한 번 더 누르거나 Enter를 눌러야 확정된다.
지연은 완전히 없앴다(`OFFER_INPUT_DELAY` 삭제).

- 전투 중 흘러든 클릭은 기껏해야 카드를 바꿀 뿐 **판을 진행시키지 못한다**
- 지연이 없으니 **아무리 빨리 눌러도 받는다**

검증: 창이 뜨자마자(지연 0ms) 클릭 → 확정까지 정상 동작 확인. 테스트 196개, 빌드 통과.

#### 별도 '결정' 버튼을 포기한 이유

처음에는 화면 아래에 결정 버튼을 따로 뒀다. **그런데 그 버튼에만 클릭 판정이
잡히지 않았다.** 카드와 똑같이 만들었는데도 커서가 바뀌지 않았고, 히트 영역을
명시해도 마찬가지였다. 세로로 전 구간을 훑어본 결과 클릭 가능한 구간은 카드
하나뿐이었다. 원인을 찾지 못했다.

눌리지 않는 버튼을 두는 것보다 판정이 확실히 동작하는 카드를 쓰는 편이 낫다고
판단해, 확정을 "고른 카드 다시 누르기"로 옮겼다. **원인 미상으로 남은 항목이다.**

#### 이 과정에서 헛돈 부분 (기록해 둘 가치가 있음)

1. **처음에 엉뚱한 원인을 지목했다.** 오버레이가 `container.setScrollFactor(0)`을
   자식을 넣기 전에 부르고 있어, 그리기와 클릭 판정이 어긋날 수 있다고 판단했다.
   그럴듯했지만 **대조군 실험에서 수정 전에도 정상 동작했다.** 가설이 틀렸다.
   (다만 그 자체로는 고쳐 둘 가치가 있어 `setScrollFactor(0, 0, true)`로 남겼다.)
2. **검증 봇이 방을 정리하지 못해 창까지 가지 못했다.** 밀도를 올린 뒤로 더 심해졌다.
   봇을 여러 번 고쳤으나 실패했고, 결국 **적을 1마리로 줄인 임시 픽스처**로 창에
   도달하는 쪽이 빨랐다. 검증용 픽스처를 먼저 만들었어야 했다.
3. **드라이버의 좌표 변환이 두 군데 틀려 있었다.** 확대가 캔버스 중심 기준이라
   생기는 오프셋(320px)을 빼먹었고, CDP 입력은 CSS 픽셀인데 백버퍼 픽셀을 보내고
   있었다(0.919배). 추측을 멈추고 `__debug`에 포인터 월드 좌표를 노출해 **직접 재서**
   맞췄다. 게임이 쓰는 값을 노출하는 편이 계산을 다시 유도하는 것보다 확실하다.

- 게임/문서 반영 여부: 코드에 반영
- 관련 파일: `src/scenes/PlayScene.ts`, `src/debug.ts`
- 남은 이슈: 결정 버튼에 클릭 판정이 잡히지 않은 원인 미상. 누르고 있던 버튼이
  창으로 흘러드는 경우는 봇이 창까지 도달하지 못해 끝까지 재현하지 못했다
  (구조상 두 번 눌러야 확정되므로 한 번 눌린 채로는 진행되지 않는다)

### 2026-07-31 - 오버레이 고정 방식 교체, 근접 사거리 판정 수정

- 단계: M6 폴리싱
- 사용 AI 도구: Claude Code (Opus 5)
- 입력 프롬프트 / 지시: 기획 담당 피드백 3건
  - "2번방에서 3번방으로 갈때 보조능력이 아예 선택이 안돼 (중략) 숫자키만 돼"
  - "2번방에서 어느 순간에 무기가 먹통되기도 하고 방향키가 먹통되기도 해"
  - (이전에 받아두고 처리되지 않았던 것) "근접공격 사거리가 너무 짧은듯. 지금 때릴려면 거의 그냥 맞을 각오하고 떄려야함"

#### 1. 선택 창 클릭이 방마다 다르게 어긋나던 문제

`scrollFactor(0)`으로 화면에 고정하면 **그리기와 클릭 판정이 서로 다른 기준을 본다.**
그리기는 컨테이너의 변환을 따르는데 클릭 판정은 자식 자신의 scrollFactor를 본다.
어긋나는 거리가 `카메라 스크롤 × 확대배율`이라 **방이 클수록 커진다.**

| 방 | 스크롤 | 화면상 어긋남 | 증상 |
| --- | --- | --- | --- |
| 1번 (폭 1900) | 300 | 450px ≈ 카드 한 칸 | 1번을 누르면 2번이 골라짐 |
| 2번 (폭 2400) | 800 | 1200px | 카드 밖으로 나가 아무것도 안 눌림 |

고정에 scrollFactor를 쓰지 않기로 했다. 컨테이너를 카메라가 보는 영역의 좌상단으로
옮겨 두면(`pinContainer`) 자식은 평범한 월드 오브젝트가 되어 **그리기와 판정이 같은
변환을 탄다.** 방 크기와 무관해진다.

**AI가 같은 곳에서 세 번 틀렸다.** 처음에는 이 scrollFactor를 원인으로 지목했다가
대조 실험에서 효과가 없어 가설을 접었고(그때 스크롤이 -320이라 어긋남이 작았다),
그래도 고쳐 둘 값어치가 있다며 `allChildren`을 켠 채로 커밋해 **한 칸 밀림 버그를
직접 만들었다.** 원인 자체는 맞았는데 검증 조건이 나빴고, 확신 없는 수정을 남긴 것이
문제를 키웠다. 사람이 방마다 증상이 다르다고 알려준 뒤에야 스크롤 크기와의 관계가 보였다.

#### 2. 무기·방향키가 먹통되던 문제

두 가지를 고쳤다.

- `update()` **맨 앞**에 오버레이 고정을 넣었는데, 여기서 예외가 나면 그 아래 전부
  (이동·조준·적 갱신)가 멈춘다. 마우스 공격만 다른 경로라 살아남아 "방향키만 먹통"으로
  보인다. 파괴된 컨테이너를 만지면 그렇게 되므로 `active` 확인을 넣었다
- 카드의 클릭 핸들러 안에서 그 카드를 즉시 파괴하고 있었다. Phaser가 아직 그 포인터
  이벤트를 처리하는 중이라 입력 플러그인이 죽은 오브젝트를 붙들고, 이후 클릭이 먹지
  않는다. 화면에서 즉시 감추고 파괴는 다음 틱으로 미룬다 (`closeOverlay`)

#### 3. 근접 사거리 — 받아두고 묻혀 있던 피드백

**이 피드백은 접수만 되고 처리되지 않은 채 로그에도 남지 않았다.**
게다가 전날 보스를 키우면서 상황이 더 나빠졌는데 그것도 놓쳤다.

원인은 판정 기준이 서로 달랐던 것이다.

- **때리기**: 중심↔중심 거리만 봄 (적 크기 무시)
- **맞기**: 중심↔중심 ≤ 플레이어 반지름 + 적 반지름 (적 크기 반영)

그래서 적이 클수록 때리기는 그대로인데 맞는 범위만 넓어졌다. 몸 표면 사이 여유:

| 적 | 반지름 | 전 | 후 |
| --- | --- | --- | --- |
| 사냥개 | 20 | 68px | 100px |
| 껍데기 | 28 | 60px | 100px |
| 문지기(보스) | 68 | **20px** | 100px |

보스는 사실상 몸에 닿아야만 때려졌다. 전날 반지름을 48→68로 키우며 40→20으로
악화된 것이다. **크기를 바꿀 때 사거리 판정을 같이 보지 않은 것이 원인이다.**

사거리를 **대상의 표면까지** 재도록 고쳤다(`range + target.radius`). 여유가
`사거리 − 플레이어 반지름`으로 고정되어 적 크기에 휘둘리지 않는다. 여기에 기본
사거리도 올렸다(검 108→120, 방패 92→104).

규칙이 "적의 중심이 반달 안" 에서 "반달이 적의 몸에 닿음"으로 바뀌었다.
**보이는 대로 맞는 쪽**이 되어, 겹쳐 보이는데 안 맞던 감각이 사라진다.

남은 어긋남 두 가지는 기록만 해 둔다.
- 적을 네모로 그리는데 판정은 원이라 모서리가 약 41% 튀어나온다
- 방패 반달은 55% 크기로 시작해 커지는데 판정은 첫 프레임에 최대 사거리로 난다

- 관련 파일: `src/render.ts`, `src/scenes/PlayScene.ts`, `src/engine/melee.ts`, `src/engine/projectile.ts`, `src/data/weapons.ts`
- 남은 이슈: 기획 담당이 준 피드백 중 접수만 되고 반영되지 않은 것이 더 있을 수 있다.
  피드백을 받으면 즉시 트래커에 항목으로 남기는 절차가 필요하다

#### 코덱스가 구현한 것

마을에서 세팅한 보조형스킬이 실제 전투까지 이어지도록 연결했다.

`configuredSupports` → `supportsFromProgress` → `loadoutFromProgress` → `run.loadout`

보조형스킬은 **콤보스킬에만** 붙는다(기본 공격 아님). 플랜대로다.
마을 진입 시 기본 세팅이 자동 장착되고, 링 메뉴 후보도 함께 채워진다
(왼손 검·방패, 오른손 활).

**마을에서 직접 고르는 UI는 아직 없다.** 지금은 하드코딩된 기본 세팅이 자동으로 붙는다.

#### 리뷰에서 잡아 고친 것

**장착 경로가 `canAttach` 검증을 건너뛰고 있었다.** 보조능력은 태그가 맞는 스킬에만
붙고 슬롯 수도 정해져 있는데, 새 경로가 그 검사를 안 거쳤다. 확인해 보니 현재
기본 세팅 5개 조합은 **우연히 전부 유효**했지만, 마을 UI로 직접 고르게 되는 순간
태그가 맞지 않는 조합이 조용히 붙어 수정자가 엉뚱하게 적용된다.

**쓰는 쪽이 아니라 읽는 쪽(`supportsFromProgress`)에 검증을 넣었다.** 어떤 경로로
설정이 들어와도 전투에 반영되기 전에 한 번은 걸러지게 하기 위해서다.

테스트 2개로 고정했다.
- 마을 진입 후 검·활·방패 콤보스킬에 각각 보조형 2개가 실제로 붙는지
- 다중투사체(투사체 전용)를 멸검(지대)에 넣으면 거부되는지

#### 리뷰에서 지적한 설계 문제 (수정하지 않고 보고)

1. **플레이어 선택이 하나도 없다.** 3택1을 폐기했는데 대체할 마을 UI가 없어,
   매 판 빌드가 동일하다. 플랜 2장의 "이번에는 활의 연사를 키워서 화면을 투사체로
   덮었다" 같은 기억이 생길 자리가 없다
2. **화이트리스트는 만들 필요가 없다.** 플랜 9장은 "당분간 콤보스킬별 허용 목록으로
   제한하고 태그 시스템은 장기 확장"이라고 적었으나, **태그 시스템은 이미 동작한다.**
   화이트리스트는 지금 있는 것보다 못한 것을 새로 만드는 셈이다
3. **보조1형/보조2형이 이름만 다르다.** 필드는 둘인데 구분하는 규칙이 없어 어느
   슬롯에 넣든 동일하게 동작한다. 그리고 2형(타 무기 시너지)에 해당하는 보조능력은
   데이터에 하나도 없다 — `상처 추적`, `균열 공명` 등은 플랜에만 있다
4. **콤보스킬 대체 발동이 선행되어야 한다.** 현재 병행 발동은 AI가 임시로 내린
   해석이고 플랜도 재설계 대상으로 적어 두었다. 보조형스킬이 콤보스킬에 붙는 구조인데
   콤보스킬이 주력이 아니면 그것을 고르는 의미도 약하다

사람이 **일정보다 완성도를 우선한다**고 방향을 정했고, 위 순서대로
`대체 발동 → 보유 개념 → 보스 드랍 → 마을 UI → 시너지 데이터 → 저장`으로 진행하기로 했다.

### 2026-07-31 - 대체 발동 준비 검증, DPS 계측기 도입

- 단계: 기획 원형 구현 플랜 #1 준비
- 사용 AI 도구: Codex(간격 정책·방 구성·문서), Claude Code Opus 5(계측기·검증)

#### 검증 요청과 결과

"지대 겹침 문제를 해결했다"는 보고를 받고 확인했다. **아직 해결이 아니라 준비였다.**

- `awakenedAttackInterval()`이 추가됐고 규칙은 맞다(지대형=별도 간격, 투사체형=기본 쿨다운)
- 그러나 `useWeapon`은 그대로 병행 발동이고, 이 함수는 **테스트에서만 불린다**
- 스탯 변경은 0건이다

대체 발동이 없으니 문제가 생길 수도 해결될 수도 없는 상태다. 규칙만 미리 정의해 둔 것이다.

#### DPS 계측기 (`src/game/dps.bench.test.ts`)

헤드리스 플레이로 밸런스를 재려다 여러 번 실패했다(봇이 방을 정리하지 못하고,
좌표 변환이 틀렸고, HMR이 측정 중 게임을 리셋했다). 그래서 **브라우저 없이 데이터와
엔진 규칙만으로 계산하는** 계측기를 만들었다. 테스트로 돌아 빠르고 깨지지 않는다.

핵심은 지대의 **겹침**이다. 지속시간 동안 여러 장이 남아 각자 틱을 돌리므로
실효 피해가 발동 주기에 반비례한다. 겹침 수 = `지속시간 / 발동간격`.

| 무기 | 기본 공격 | 각성 | 단일 대상 | 무리 |
| --- | --- | --- | --- | --- |
| 검 | 153 | 181 | 1.18배 | 2.94배 |
| 활 | 231 | 906 | 3.92배 | 3.92배 |
| 비전 | 232 | 821 | 3.55배 | 3.55배 |
| 방패 | 90 | 100 | 1.11배 | 4.23배 |

**AI가 앞서 두 번 틀렸던 것을 이 계측기가 바로잡았다.**

1. 처음에는 "대체 발동하면 지대형이 약해져 콤보 달성이 손해가 된다"고 경고했다.
   근거로 든 측정치는 **적 체력 120·5마리 시절의 것**인데 지금은 52·12마리다.
   조건이 통째로 바뀐 옛 결과를 현재 사실처럼 말했다
2. 그다음에는 지대 **겹침을 계산에 넣지 않아** 멸검 DPS를 65로 봤다. 실제로는
   2.8장이 겹쳐 181이다. 사람이 "지금도 콤보스킬이 센 것 같은데"라고 지적해 다시 쟀다

두 번 다 **사람의 관찰이 AI의 계산보다 정확했다.** 재기 전에 단정한 것이 원인이다.

#### 계측기가 드러낸 진짜 문제

지대 겹침 폭증은 `awakenedAttackInterval`이 막는다(멸검 542 → 181, 3배).
그런데 그 규칙이 과교정을 낳았다. **단일 대상에서 지대형은 각성해도 1.1~1.2배뿐이고
투사체형은 3.5~3.9배다.** 무기 사이 각성 가치가 3.5배 벌어진다.

첫 문지기가 2번째 방이고 보스는 단일 대상이라, **검 1종으로 시작하는 플레이어는
각성이 사실상 무의미한 상태로 첫 보스를 잡아야 한다.**

완료 기준 테스트(`각성 배율 최대/최소 < 2.5배`)는 현재 3.5배로 실패하므로
**skip 처리**했다. 실패한 채로 두면 구현자가 자기 회귀와 구분할 수 없다.
재조정을 시작할 때 skip을 풀고 통과시킨다.

**주의: 계측값은 상한이다.** "적이 계속 맞고 있다"를 가정한다. 실제로는 적이 지대에서
걸어 나가고 투사체는 빗나간다. 무기 사이 상대 비교용이지 절대값이 아니다.

#### 함께 고친 것 — 마지막 보스 방 제거

리뷰에서 플랜 4장의 예선형 루프와 실제 방 구성이 다르다고 지적했다. 문서엔 보스가
1회인데 실제로는 4번째 방도 보스였고, **두 번째 보스는 드랍해도 쓸 곳이 없었다**
(잡는 즉시 게임 종료). 코덱스가 마지막 보스 방을 `파편 회랑`(사냥개 18, 몰이꾼 5,
껍데기 3)으로 바꿔, 첫 보스 뒤 얻은 활/방패와 R키 교체를 시험하는 전투방이 됐다.
한 판에 보스는 1회이고, 그 보스가 성장의 원천이라는 구조가 분명해졌다.

### 2026-07-31 - 최종 보스 방 복구 (AI 판단 오류 교정)

- 단계: 방 구성
- 사용 AI 도구: Claude Code Opus 5
- 입력: 사람의 질문 - "이게 기획자의 의도와 맞는거야?"

#### 무엇이 잘못됐나

**AI가 기획 의도에서 멀어지는 방향으로 구조를 깎자고 제안했고, 그대로 반영됐다.**

기획 담당의 원래 말은 이랬다.
> 잡몹 수량이 엄청 많고 걔네는 그냥 다 쉽게 썰면서 나아간 다음에 **여러 보스들을 잡아
> 아이템을 얻는** 걸 생각했음 / 보스는 한 종류로 하면 **절대** 안될듯

그런데 AI는 마지막 보스 방을 없애자고 했다. 근거는 **"두 번째 보스는 드랍해도 쓸 곳이
없다 — 잡는 즉시 게임이 끝난다"**였다. 그 결과 한 판에 보스가 1회가 되고,
**게임이 잡몹 방 정리로 끝났다.**

#### 근거 자체가 틀렸다

"쓸 곳이 없다"는 **localStorage 저장이 아직 없어서** 생긴 제약이다. 플랜 11장이
정확히 그 문제를 풀려고 존재한다 — 보스 드랍은 영구 성장이고, 저장이 들어오면
최종 보스 드랍은 다음 판에서 쓰인다.

즉 **아직 만들지 않은 기능이 없다는 이유로, 그 기능이 들어오면 사라질 문제를 근거 삼아
구조를 깎았다.** 사람이 "일정은 신경 쓰지 말고 완성도만 생각하라"고 방향을 정한 직후에
벌어진 일이라 더 어긋난다.

사람이 "이게 기획자의 의도와 맞는거야?"라고 물어 바로잡혔다. **오늘 세 번째로
사람의 확인이 AI의 판단보다 정확했던 사례다.**

#### 복구한 구조

```
흐린 입구(잡몹) → 첫 문지기(보스 A, 해금+마을) → 해금 시험장
  → 파편 회랑(엘리트) → 무너진 문(보스 B, 최종)
```

- 보스 A = **해금**의 순간. 활/방패를 주고 마을로 보낸다
- 보스 B = **마무리**의 순간. 영구 성장 드랍을 준다 (드랍 자체는 아직 미구현)

판이 보스전으로 끝나 마무리가 서고, 기획의 "여러 보스"가 한 판 안에서 성립한다.
다만 **아직 보스는 1종**이라 같은 적을 두 번 만난다. 플랜 Stage F(보스 2종화)가
이 구조에 그대로 들어가면 해소된다.

#### 남길 교훈

**미구현 기능을 제약으로 삼아 설계를 축소하지 않는다.** "지금 그게 없으니 이건 의미
없다"는 판단은, 그 기능이 로드맵에 있으면 틀린 판단이다. 축소를 제안하기 전에
"이 제약이 영구적인가, 아직 안 만든 것뿐인가"를 먼저 봐야 한다.
