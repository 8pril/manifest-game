# AI 활용 기록 로그

이 파일은 최종 제출물인 `AI 활용 기술 문서` 작성을 위한 원천 기록이다.  
AI를 사용한 모든 의사결정, 프롬프트, 결과, 사람의 검토 및 수정 내용을 이곳에 누적한다.

## 기록 원칙

- AI를 사용한 즉시 기록한다.
- 프롬프트는 가능한 한 원문에 가깝게 남긴다.
- AI 결과물을 그대로 사용했는지, 수정했는지, 폐기했는지 명확히 적는다.
- 게임에 반영된 결과와 반영되지 않은 결과를 구분한다.
- 저작권, 라이선스, 외부 출처 관련 내용은 빠뜨리지 않는다.
- 주요 작업이 끝났는데 기록할 내용이 없다고 판단한 경우, 최종 응답에서 그 이유를 명시한다.
- 이 프로젝트의 작업 규칙은 루트의 `AGENTS.md`에도 기록되어 있으며, 작업 종료 전 이 파일 업데이트 여부를 확인한다.

## 단계별 기록 액션

- [ ] AI에게 기존 기획의 핵심 루프 요약을 요청했다.
- [ ] AI가 제안한 스코프 축소안을 검토했다.
- [ ] 채택한 기능과 제외한 기능을 기록했다.
- [ ] 사람이 최종 결정한 이유를 기록했다.

기록해야 할 내용:

- 기획 요약 프롬프트
- AI가 제안한 핵심 재미 요소
- 예선 빌드에서 제외한 기능
- 최종 선택 이유

### Phase 1. 프로젝트 세팅

- [ ] 기술 스택 후보 비교에 AI를 사용했다.
- [ ] 선택한 스택과 선택 이유를 기록했다.
- [ ] AI가 생성 또는 제안한 초기 구조를 기록했다.
- [ ] 사람이 수정한 프로젝트 구조를 기록했다.

기록해야 할 내용:

- Vite, Phaser, Canvas 등 후보 비교

### Phase 2. 핵심 플레이 구현

- [ ] 핵심 게임 루프 구현에 AI를 사용했다.

기록해야 할 내용:

- 플레이어 조작 구현
- 전투/점수/자원/턴/웨이브 로직
- 승리/패배 조건
- 버그 원인과 수정 이유

### Phase 3. 콘텐츠 채우기

- [ ] 무기, 상태이상, 콤보 발동 스킬, 보조능력 데이터 작성에 AI를 사용했다.
- [ ] 태그 기반 장착 가능 여부와 조합 규칙 설계에 AI를 사용했다.
- [ ] 사람이 편집, 검증, 밸런싱한 내용을 기록했다.
- [ ] 최종 게임에 반영된 AI 코딩 에이전트 활용 사례를 정리했다.

기록해야 할 내용:

- AI로 만든 무기 데이터, 보조능력 데이터, 적 패턴, 웨이브, 밸런스 초안

- 결과물 중 채택/수정/폐기 항목

### Phase 4. 폴리싱 및 안정화

- [ ] UI 문구, 튜토리얼, 밸런스 조정에 AI를 사용했다.

**1차 시도 (Codex) — 효과 없음**

- 처음에는 `devicePixelRatio` 기반 `resolution` 옵션이 이상적이라고 판단했으나, Phaser 4 `GameConfig`에 해당 옵션이 없어 타입 검사에서 실패해 되돌림
- 논리 해상도를 1920×1080으로 올리면 게임장 크기와 이동 속도 체감이 달라질 수 있다고 보아 보류하고, 대신 `pixelArt: false`, `antialias: true`, `antialiasGL: true`, `roundPixels: false`를 최상위에 명시하는 보수적 조치를 적용
- 빌드와 테스트는 통과했고 선명도 보강으로 보고되었다

**검증 (Claude Code) — 1차 시도가 무효임을 확인**

- 사람이 "적절한 수정이야?"라고 물어, 주장을 검증하기 위해 CDP로 캔버스 실측
- DPR 2 환경에서 백버퍼 1280×720이 물리 픽셀 2052×1154로 표시되어 **확대 배율 1.6배**. 이것이 흐릿함의 원인이었다
- 추가된 네 옵션은 Phaser가 백버퍼 **안에** 그리는 방식을 정할 뿐, 브라우저가 그 버퍼를 화면으로 늘릴 때의 보간에 관여하지 않는다. 게다가 넷 다 Phaser 기본값이고 `pixelArt`와 `antialias`는 이미 `render: {}`에 있었다. 즉 동작이 전혀 바뀌지 않는 중복 설정이었다
- 무해하지만 무효였고, 보고 내용이 실제 효과보다 과장되어 있었다

**2차 시도 (Claude Code) — 실제 해결**

- 흐릿함은 백버퍼 크기 문제이므로 백버퍼를 키우는 것 외에 방법이 없다. 다만 논리 해상도를 그대로 1920×1080으로 올리면 모든 위치·속도·크기 상수가 함께 흔들린다는 1차 판단은 옳았다
- 그래서 **월드 좌표계와 캔버스 크기를 분리**했다. `GAME_WIDTH/HEIGHT`는 1280×720 그대로 두고, `CANVAS_WIDTH/HEIGHT`를 `RENDER_SCALE`(1.5)배로 잡아 백버퍼만 1920×1080으로 키웠다. 각 씬에서 카메라를 같은 배율로 확대하고 스크롤을 보정해, 화면에 보이는 월드 영역은 정확히 1280×720으로 유지된다

- 순서에 대한 판단: Codex는 "아트 생성 전에 하는 게 맞다"고 했고 결론은 같지만 근거는 달랐다. `docs/art-spec.md`의 14장은 캐릭터·투사체·지대·바닥이고 이펙트 에셋이 없으므로 두 작업은 서로 막지 않는다. 지금 해야 하는 실제 이유는 **플레이 테스트 인계** 때문이다. 상태 시스템이 보이지 않는 상태로 넘기면 기획 담당이 그것을 인지하지 못한 채 평가하게 되어, 가장 희소한 자원인 사람의 플레이 시간에서 얻는 정보가 줄어든다
- 데미지 숫자 범위 조정: Codex는 데미지 숫자를 제안했으나 모든 타격에 띄우면 적 12마리에 다중투사체까지 붙었을 때 화면이 숫자로 덮인다. **규칙 때문에 추가로 들어간 피해에만** 띄우도록 좁혔다(상처 폭발 +90, 벽 충돌 +40). "왜 갑자기 크게 들어갔지"에 답하는 것이 목적이므로 그 순간에만 정보가 붙으면 된다
- 수정한 내용: `src/effects.ts`를 만들어 링 확산, 플래시, 떠오르는 숫자, 충격(링 + 약한 화면 흔들림)을 모았다. 전부 Phaser 도형과 트윈이라 아트 에셋에 의존하지 않으며, 나중에 스프라이트가 들어와도 이 파일만 고치면 된다. 상처 폭발·낙인 소모·벽 충돌 세 지점에 배선하고, 비전 흐름이 걸린 동안 플레이어를 감싸는 오라를 추가해 남은 시간에 따라 옅어지게 했다. 카메라 확대가 걸려 있어 화면 흔들림은 약하게만(0.003, 120ms) 넣었다
- **검증 중 발견한 설계 문제**: 봇으로 상처 폭발을 재현하려다 실패했고, 계산해보니 구조적으로 불가능한 조합이 있었다. 베기 피해 46 기준으로 추적자(체력 120)는 3타, 사수(90)는 2타에 죽어 **5스택에 도달하기 전에 죽는다.** 중장갑(7타)과 보스(35타)에서만 발동한다. 즉 웨이브 1에서는 상처 폭발을 한 번도 볼 수 없다. 원안의 5스택 규칙은 그대로지만 적 체력과 무기 피해는 AI가 정한 값이므로, 이 불일치는 AI가 만든 것이다
- 판단 보류: 이대로 "단단한 적을 무너뜨리는 마무리"로 두는 것도 설계로서 말이 되므로 수치를 임의로 바꾸지 않고 `docs/playtest-brief.md`에 확인 항목으로 넘겼다
- 검증의 한계: 빌드와 테스트는 통과했고 콘솔 에러도 없으나, **폭발·충격 연출이 실제로 그려지는 프레임을 스크린샷으로 잡지 못했다.** 헤드리스 봇이 조준을 고정 좌표로 하고 이동하지 않아 보스전에서 10초 내에 죽는다. 연출을 띄우는 조건은 피해량을 바꾸는 조건과 동일하고 그 동작은 확인되었으므로 로직은 맞지만, 표시 여부는 사람이 확인해야 한다

- 초기 오독: 스모크 런에서 활·비전 왼손 판이 모두 `wave 4/4, 처치 33`으로 끝나, 전체 적 수(33마리)와 일치하는 것을 보고 "다 죽였는데 승리로 전이되지 않는 버그"를 의심했다. 확인 결과 판당 제한시간 50초에 걸려 승리 직전에 잘린 것이었다. 제한시간을 늘려 재실행하니 45.6초에 정상적으로 `won`으로 전이했다. **수치가 우연히 일치할 때 버그로 단정하지 않고 재현 조건을 바꿔 확인한 것이 맞았다**

### 2026-07-29 - 전투 문구 표기 수정 (부호 오용)

- 단계: M6 폴리싱
- 사용 AI 도구: Claude Code (Opus 5)
- 목적: 추가 피해 표시가 회복으로 읽히는 문제를 고친다
- 입력 프롬프트 / 지시: "데미지면 +가 아니라 - 아니야?", "니 생각은 ? +가 적절한가?"
- 사람이 지적한 문제: AI가 추가 피해를 `+90`, `+40`으로 표시했다. "추가로"라는 의미를 부호 자리에 담은 것인데, **적 위에 뜨는 `+`는 관습상 회복이나 보호막으로 읽힌다.** 의미를 담으려다 표기 관습을 깨서 정반대로 전달되는 상태였다
- AI의 판단: `-40`으로 바꾸는 최소 수정도 절반짜리다. 이 문구를 넣은 목적이 "왜 갑자기 크게 들어갔는지" 알리는 것인데 `-40`은 그 답을 하지 못하고, 플레이어는 40이 큰 값인지 판단할 기준도 없다. 수치보다 **원인**이 중요하다
- 수정한 내용: 부호를 없애고 규칙 이름을 함께 표시하도록 바꿨다. `+90` → `상처 폭발 90`, `+40` → `벽 충돌 40`. 이 문구는 자주 뜨지 않으므로(폭발은 중장갑·보스에서만, 벽 충돌은 방패로 벽에 몰 때만) 글자가 길어져도 화면이 지저분해지지 않고, 오히려 처음 보는 심사자가 상태 시스템의 존재를 알아채는 지점이 된다. 함수 이름도 `floatingNumber` → `floatingText`로 바꿨다
- 추가 수정: 첫 촬영에서 문구가 흰 플래시와 겹쳐 읽기 어려웠다. 가장 읽혀야 할 순간이므로 적의 반경만큼 위에서 띄우도록 조정하고 재확인했다
- 검증: 보스전에서 `상처 폭발 90` 문구가 겹침 없이 표시되는 프레임을 스크린샷으로 확보
- 게임/문서 반영 여부: 코드에 반영
- 관련 파일: `src/effects.ts`, `src/scenes/PlayScene.ts`
- 배운 것: 표기 관습을 깨면서까지 의미를 압축하려 하면 정반대로 읽힐 수 있다. 이 경우 부호 하나를 아끼는 대신 단어를 쓰는 편이 명확했다
